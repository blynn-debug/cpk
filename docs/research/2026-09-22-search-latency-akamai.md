# 키워드 검색 지연·프록시·Akamai 기술 조사

조사일: 2026-09-22 KST. 코드 기준: `63188fe`.

**판단: 유료 프록시는 도움이 될 수 있지만, 현재 1~2분 지연을 프록시 교체만으로 해결할 근거는 없다. 브라우저 대기·세션 생성·재시도·후속 조회를 먼저 계측하고 줄인 뒤, 관리형 수집 서비스와 비교하는 것이 타당하다.**

이번 작업은 코드 분석, 운영 설정·기존 로그의 읽기, 공식 기술 문서 조사다. 실제 쿠팡 검색, 유료 서비스 호출·구매, 운영 코드 변경·배포는 실행하지 않았다. 따라서 아래 시간은 **설정값·코드상 대기 구조·개선 목표**이며, 새로 측정한 검색 지연이나 개선 성과가 아니다.

주로 마켓 레이더를 기준으로 분석하되 기본 검색 경로도 확인했다. 사용자에게 어느 화면인지 질문했으나 작성 시점에 답변이 없어 두 경로를 구분했다.

**확인한 운영 상태**

- 맥미니의 `cpk_browser.py`, `cpk_market_parallel.py`, `deploy/cpk_ssh_search.sh`는 로컬 파일과 SHA-256이 일치했다.
- 운영 환경에 프록시가 설정되어 있다. 자격증명은 출력·저장하지 않았다. 운영 문서는 Proxy-Cheap 한국 주거 프록시 사용을 설명한다. 실제 결제 상품·출구 품질은 확인하지 않았다.
- 웹 래퍼의 실효 설정은 요청 간격 5초, 워밍업 8초, sticky 활성화, TTL 10분이다. 소스 기본값 20초·12초와 다르다.
- 마켓 레이더는 `collect_parallel(..., workers=1)`을 호출한다. 배치 기본 워커 6개를 늘려도 단건 검색은 빨라지지 않는다.
- 기존 운영 로그에는 병렬 배치 `7/9 성공`, 이후 `10건 paused`, 이후 `3/10 성공`이 있다. 서로 다른 시점·입력이므로 성공률 비교 실험으로 사용할 수 없다. 프록시 사용 중에도 실패가 발생했다는 근거만 된다.
- 현재 마켓 응답에는 단계별 시간 계측이 없다. 기본 검색의 `elapsed_ms`도 크롤러 내부 합계이며 사용자 클릭부터 표시까지의 시간은 아니다.

**현재 완료 경로와 병목**

마켓 레이더 단건은 다음 순서로 실행된다.

```text
웹 POST → SSH 중계 → Chrome 상태 확인
→ 새 시크릿 컨텍스트·프록시 인증 준비
→ 홈 로드 → settle → 워밍업
→ 검색 로드 → settle → 판정
→ 실패 시 새 컨텍스트로 위 과정 1회 재시도
→ 별도 HTTP 세션의 자동완성
→ 결과 파싱·DB 저장·점수
→ 도매꾹 조회 → 전체 리포트 → 웹 표시
```

| 확인된 구조 | 시간·문제 | 코드 근거 |
|---|---|---|
| 검색마다 새 컨텍스트 | 이전 검색의 쿠키·워밍업 상태를 재사용하지 못함. sticky TTL 10분도 컨텍스트를 매번 닫으면 검색 간 재사용으로 이어지지 않음 | `cpk_market_parallel.py:57`, `cpk_browser.py:151` |
| 홈·검색 모두 전체 load 이벤트 대기 | 각 탐색의 명목 timeout 40초. 상품/연관검색어가 준비되어도 다른 리소스 때문에 늦어질 수 있음 | `cpk_browser.py:285` |
| 로드 뒤 무조건 settle | 첫 시도 홈 3~6초 + 검색 3~5초 = **6~11초**. 재시도는 홈 3~6초 + 검색 5~8초 = **8~14초** | `cpk_browser.py:309`, `cpk_market_parallel.py:62` |
| 워밍업 | 웹 설정 8초. 조기 종료가 있어 항상 8초를 쓰는 것은 아님. 폴링·CDP 호출 때문에 엄밀한 총시간 상한도 아님 | `cpk_browser.py:186`, `deploy/cpk_ssh_search.sh:15` |
| 재시도 | 실패하면 홈 방문·워밍업·검색을 새로 수행. 단건에도 최대 두 번 | `cpk_market_parallel.py:42` |
| 자동완성 후 도매꾹을 순차 조회 | 각 timeout 설정 25초·20초. 앞에서 검색에 성공했어도 이 후속 조회가 끝나야 화면에 표시됨. 정상 응답이 매번 이만큼 걸린다는 뜻은 아님 | `cpk_session.py:236`, `cpk_market_parallel.py:80`, `cpk_market_parallel.py:134`, `cpk_domeggook.py:44` |
| UI가 전체 JSON을 기다림 | 연관검색어·상품이 준비되어도 먼저 표시할 수 없음 | `web/templates/markets.html:238` |

따라서 마켓 지연은 대략 `SSH + 시도별(컨텍스트 + 홈 + settle + 워밍업 + 검색 + settle) + 자동완성 + 도매꾹 + 저장/리포트`다. 40초 대기나 재시도가 하나만 포함되어도 분 단위가 가능하다. 어느 항목이 운영 지연의 몇 %인지는 아직 모른다.

**우선 검증할 구현 결함 후보**

1. **Fetch 이벤트 처리가 sleep 동안 멈춘다.** 인증 프록시 경로는 `Fetch.enable(patterns=[*])`로 모든 요청을 가로채고 이벤트 처리기가 `continueRequest` 등을 보낸다. 그런데 `goto()`/`submit_search()` 마지막은 `time.sleep()`이다. 그때 도착한 요청은 다음 이벤트 처리 때까지 멈출 수 있다. Chromium 프로토콜도 가로챈 요청은 클라이언트가 계속/실패/응답 명령을 보낼 때까지 정지한다고 명시한다. 코드와 프로토콜상 문제 가능성은 확인했지만, 운영에서 추가된 시간은 미측정이다. [Chromium Fetch 프로토콜](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Fetch.pdl)
2. **기본 검색은 홈 워밍업이 중복된다.** `search_session()`에서 공유 탭을 워밍업하고, 프록시가 있으면 실제 검색에 별도 시크릿 컨텍스트를 만들어 또 홈을 방문한다. 앞선 워밍업은 실제 검색 컨텍스트를 준비하지 않는다. 공유 `Tab()`에는 시크릿 탭의 프록시 인증 처리도 없다. 중복 방문은 코드로 확인되며, 추가 인증 대기 여부는 실측해야 한다. 마켓 병렬 경로에는 이 바깥 워밍업이 없다. 근거: `cpk_browser.py:479`, `:484`, `:505`, `:515`.
3. **40초는 전체 탐색의 확실한 마감 시간이 아니다.** `Page.navigate` 호출은 타이머 시작 전이고, `recv()`는 남은 시간이 아닌 전체 timeout을 사용한다. 마지막 이벤트 뒤 한 번 더 긴 수신 대기가 생길 수 있다. 명령 응답 대기도 총시간 제한이 별도로 없다. 절대 마감 시각을 기준으로 남은 시간을 전달해야 한다.
4. **준비 완료 판단이 약하다.** `_abck` 내부 필드 하나를 비교한 결과를 검증 완료로 간주한다. 이번에 확인한 공식 문서에서 그 값의 보장된 의미는 찾지 못했다. 쿠키 판정만으로 성공을 보장하지 말고, 요청한 검색어의 실제 페이지와 필수 데이터로 판정해야 한다.

기본 검색의 공통 관문은 직전 작업이 끝난 뒤 다음 시작까지 간격을 둔다. 웹에서는 5초지만 마켓 `fetch_one()`은 이 직렬화 관문을 사용하지 않는다. 따라서 마켓의 1~2분을 20초 간격 탓으로 설명하거나 간격만 낮추는 것은 맞지 않는다.

**유료 프록시가 해결하는 범위**

Akamai는 헤더 순서·브라우저 버전 불일치 같은 요청 특성, 브라우저 확인, 제품·설정에 따른 행동 신호 등을 이용한다. IP 변경만으로 이 모든 요소가 바뀌지는 않는다. 이는 제품의 일반 동작이며 쿠팡이 어떤 규칙으로 이번 요청을 차단했는지는 관측하지 못했다. [Akamai Detection methods](https://techdocs.akamai.com/cloud-security/docs/detection-methods), [Bot Manager](https://www.akamai.com/products/bot-manager)

| 선택지 | 기대할 수 있는 역할 | 이번 시스템에서의 한계 |
|---|---|---|
| 한국 주거 프록시 교체 | 출구의 연결 품질·대역폭·평판이 문제일 때 개선 가능 | 코드의 sleep·중복 워밍업·순차 조회는 그대로. 비싼 요금이 쿠팡 성공률이나 지연을 보장하지 않음 |
| 한국 ISP/고정 주거 프록시 | 안정된 출구를 확보할 경우 세션 재사용에 유리할 수 있음 | 한국 재고·실제 위치·공유 여부·차단 상태를 확인해야 함. 고정 IP 하나에 요청이 집중될 수 있음 |
| 회전형 sticky + 유지되는 브라우저 컨텍스트 | 같은 세션을 반복 사용해 초기 준비 비용을 나눌 수 있음 | 컨텍스트와 출구를 함께 유지해야 함. 주거 장치가 사라지면 sticky 중에도 IP가 바뀔 수 있음 |
| 관리형 Unlocker / Browser / Scraper API | 업체가 브라우저·프록시·차단 대응·재시도를 관리 | 내부 재시도로 늦을 수 있음. 필요한 데이터와 응답 시간은 별도 검증 |

Sticky는 일정 시간 같은 출구를 요청하는 기능이지 영구적으로 IP를 보장하는 계약이 아니다. 공급사도 장치 이탈로 IP가 바뀔 수 있다고 설명한다. [Proxy-Cheap FAQ](https://support.proxy-cheap.com/hc/en-us/articles/38182068823837-Proxy-Cheap-Frequently-Asked-Questions)

현재 `_session-..._ttl-...`를 비밀번호에 덧붙이는 코드는 특정 공급사 형식을 전제한다. 다른 업체를 시험할 때 주소·비밀번호만 바꾸면 세션 제어가 오동작할 수 있으므로 공급사별 설정을 분리해야 한다. 또한 서로 다른 session ID가 반드시 서로 다른 출구 IP라는 보장은 없다. 현 코드의 “워커별 IP가 다르므로 병렬 차단 위험이 증가하지 않는다”는 주석은 검증된 사실로 취급하지 않는다.

**Akamai 대응 기술의 실용성**

- **실제 브라우저 + 일관된 세션 유지:** 현재 구조를 활용할 수 있는 우선 후보다. IP·쿠키·브라우저를 함께 유지하고, 성공한 컨텍스트는 요청이 있는 동안 재사용한다. 사용자의 검색을 바꿀 수 있는 개인화 영향도 함께 비교한다. 매번 초기화하는 방식보다 얼마나 유리한지는 A/B 측정이 필요하다.
- **브라우저가 이미 받은 응답 활용:** CDP 네트워크 응답 또는 준비된 DOM에서 필요한 검색 데이터를 먼저 읽는다. 모든 광고·미디어 로드가 끝날 필요가 있는지 확인한다. `DOMContentLoaded`만으로 결과 완료를 가정하지 않고 검색어 일치·필수 필드·정상 무결과/챌린지 상태를 검사한다. 연관검색어가 늦게 생성될 수 있으므로 상품 노출만 보고 수집을 닫으면 안 된다.
- **TLS/HTTP 클라이언트 모사:** 이미 `curl_cffi` 보조 경로가 있다. 브라우저의 JS 실행과 세션 연속성까지 대체하지는 않으므로 모사 옵션 교체만으로 해결된다고 볼 수 없다. 관측된 공개 데이터 경로가 실제로 같은 결과를 제공할 때 선택적으로 사용한다.
- **관리형 차단 대응:** 자체 브라우저 운용 부담을 업체에 맡기는 선택이다. 쿠팡 검색 페이지를 실제로 처리하는지, 한국 지역을 유지하는지, 연관검색어·자동완성을 누락하지 않는지를 우선 확인한다.
- **센서 프로토콜 역공학·자체 solver:** 조사 대상으로는 존재하지만, 지속적인 프로토콜 변경 대응과 버전 관리가 필요하다는 공학적 판단이다. 이번 조사에서 운영 가능한 쿠팡 전용 구현·지속 성공률을 검증하지 못했다. 단건 검색 속도 개선의 첫 투자 대상으로 추천하지 않는다.
- **공식 데이터 경로·협의된 접근:** 이용 가능한 공식 API가 필요한 필드를 제공한다면 운영상 가장 단순해질 수 있다. 다만 판매자 Open API의 상품·주문 관리 기능을 소비자 검색 순위·연관검색어·자동완성과 같다고 볼 수 없다. Partners 문서는 이번 접근에서 JS 셸만 반환해 최신 필드·한도를 확인하지 못했다. [Coupang Developer Center](https://developers.coupang.com/ko), [Partners](https://partners.coupang.com/#help/open-api)

**권장 구현 순서**

1. **단계별 시간부터 남긴다.** `request_id`, 경로, 시도 번호, SSH, 컨텍스트 생성, 홈, 워밍업, 검색, 자동완성, 도매꾹, DB/리포트, 전체 시간을 `monotonic()`으로 측정한다. 성공/무결과/챌린지/네트워크 실패와 재시도 시간을 함께 기록한다. 프록시 자격증명·쿠키 원문은 기록하지 않는다.
2. **이벤트 처리와 완료 조건을 수정한다.** 인증 프록시 경로에서 sleep 동안에도 Fetch 이벤트를 처리하고, 기본 검색의 중복 워밍업을 제거한다. 필수 데이터가 준비되면 고정 settle을 조기에 끝내며, 모든 단계에 남은 총시간을 전달한다. 단순히 timeout을 낮춰 실패가 빨리 나오는 것을 성능 향상으로 계산하지 않는다.
3. **사용자가 필요한 결과부터 표시한다.** 연관검색어·자동완성이 이 프로젝트의 핵심이므로 상품보다 낮은 우선순위로 밀지 않는다. 가능한 독립 조회는 예산·중단 상태를 확인해 함께 진행하고, 준비된 키워드/검색 결과를 표시한다. 도매꾹은 별도 상태로 갱신할 수 있다. 실패한 자동완성을 정상 빈 목록으로 표시하지 않는다. 첫 표시 시간과 필수 데이터 완료 시간은 별도로 측정한다.
4. **세션 재사용을 소규모로 비교한다.** 온디맨드 요청을 받는 상주 워커가 브라우저 컨텍스트를 보유해야 한다. 지금은 SSH마다 Python을 새로 실행하고 컨텍스트를 닫기 때문에 모듈 전역 캐시만 추가해서는 요청 간 재사용이 되지 않는다. 검색이 없을 때 쿠팡에 주기적으로 접근할 필요는 없다. 제한 화면·세션 만료·품질 저하 시의 정리 조건을 명시한다.
5. **이후 공급사 비교를 한다.** 현재 프록시를 유지한 개선판과 한국 출구의 대체 프록시, 관리형 서비스 한 곳을 같은 필수 데이터 계약으로 비교한다. 실패 후 여러 업체를 끝없이 이어 붙이면 응답 시간이 다시 늘어나므로 전체 마감 시간과 재시도 횟수를 공유한다.

짧은 TTL의 결과 캐시는 재검색에 효과가 있지만, 새 검색의 완료 시간이 빨라진 것은 아니다. 저장 시각을 표시하고 명시적인 새로고침을 제공한다. 초기 TTL 후보는 5~10분이며, 시장 데이터 신선도 요구를 확인한 뒤 결정한다.

**비교 실험과 완료 기준 제안**

- 1차는 같은 대표 키워드 5개를 현재판과 대기 개선판에 각 1회 실행하는 작은 진단으로 시작한다. 실행 순서를 섞고 기존 중단·요청 예산을 반영한다. 이 표본으로 p95나 신뢰도 높은 성공률을 주장하지 않는다.
- 필수 항목: 검색어 일치, 정상 결과/정상 무결과, 관련어와 자동완성의 성공 상태, 상품 순서·광고·배지·가격·리뷰의 보존. 도매꾹은 따로 측정한다.
- 측정값: 첫 유효 표시 시간, 필수 데이터 완료 시간, 전체 완료 시간, 최초 시도 성공률, 최종 성공률, 재시도 수, 키워드당 전송량·비용. 성공 요청의 지연과 전체 요청의 실패/대기 비율을 함께 보고한다.
- 확대 검증은 실제 온디맨드 사용에 계측을 붙여 진행한다. 충분한 표본이 모인 뒤 p50/p95를 비교하고 표본 수를 함께 제시한다.
- 초기 성능 목표 제안: **새 검색의 필수 데이터 완료 p50 20초 이내, p95 45초 이내**, 기존 대비 성공률·데이터 완전성 유지. 이는 합의·실측 전 목표이고 달성을 보장하지 않는다. 캐시 적중과 부분 표시 시간은 이 지표에서 분리한다.
- 비용은 `총 실제 청구 비용 / 필수 데이터를 정상 제공한 검색 수`로 비교한다. 저렴한 GB 가격이나 record 단가만으로 공급사를 결정하지 않는다.

**조사 한계와 재현 근거**

운영 설정·과거 로그는 읽었지만 단계별 실행 계측은 하지 않았다. SSH 구간, 프록시 출구, Chrome CPU/메모리, Akamai 응답 대기 중 어느 것이 지배적인지는 아직 미확정이다. 기존 운영 문서의 “error403은 IP 평판”, “센서 쿠키만 검증되면 해결” 같은 문구도 이번 관측만으로 원인으로 확정할 수 없다.

외부 문서 수집은 사용자 지침에 따라 로컬 `insane-search` README와 CLI를 먼저 확인·시도했다. 현재 Python 환경에 `curl_cffi`·PyYAML이 없고 기본 출력 인코딩 문제가 있어 본문 수집이 되지 않았다. UTF-8 실행으로 의존성 부재를 확인한 뒤 웹 도구의 공식 원문을 보완적으로 사용했다. 의존성 부재를 대상 사이트 차단으로 해석하지 않았다.

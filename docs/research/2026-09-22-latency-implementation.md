# 검색 지연 개선 실행 기록

목표: 검색 결과의 정확성을 유지하며 필수 데이터 완료 시간을 줄이고, 준비된 결과를 먼저 표시한다.

사용자가 승인한 0~4단계에 따라 계측, 대기 수정, 진행형 표시, 요청 간 브라우저 재사용,
공급사 비교 실행 도구를 구현한다. p50 20초/p95 45초는 검증할 목표이며 달성 사실로 간주하지 않는다.

설계: 기존 평면 모듈 구성을 유지한다. 계측(`cpk_metrics`), 브라우저 세션과 검색
(`cpk_engine`), 온디맨드 작업과 로컬 소켓 서버(`cpk_worker`), 비교 실행(`cpk_benchmark`)을 분리한다.
맥미니 상주 워커는 외부 포트 없이 사용자 전용 Unix 소켓으로 SSH 호출을 받는다.
작업 조회는 새 쿠팡 요청을 만들지 않는다. 중복 요청 ID는 같은 작업을 반환한다.
동일 키워드의 진행 중 요청은 합치고, 대기열은 제한한다. 재시작 시 진행 중 작업을 실패로 전환해
결과가 없는 작업이 영원히 실행 중으로 남지 않게 한다. 완료 결과와 단계 상태는 명시적으로 구분한다.

검증 조건:

- Fetch 요청이 settle 중에도 진행됨. load 이벤트가 navigate 응답보다 먼저 와도 유실되지 않음.
- 명령·탐색·준비 판정은 하나의 절대 마감 시간을 공유함. 0/만료 직전/만료 경계를 검사.
- 새 컨텍스트 1회 준비, 정상 검색 후 재사용, TTL/차단/통신 실패 뒤 폐기.
- 중단·예산 소진 시 홈·검색·자동완성의 새 요청이 시작되지 않음.
- 상품·연관검색어·자동완성·도매꾹의 완료/실패/진행 중을 구분하고 부분 결과를 보존.
- 빈 입력·최대 길이·비정상 입력, 중복 시작·중복 조회, 동시 요청, 대기열 포화, 재시작 복구.
- 웹 인증을 시작과 조회 모두 적용. 사용자 전환 후 이전 검색 응답이 새 화면을 덮지 않음.
- 브라우저 준비 판정은 실제 검색어/페이지/상품 또는 명시적 무결과에 근거함.
- 공급사 비교는 동일 필수 데이터 계약을 검사하며 표본이 적으면 p95를 성과로 표시하지 않음.

실행 계층: 기존 오프라인 회귀 + 새 단위/통합 + Playwright 진행형 UI + 맥미니 소규모 실측.
외부 서비스 자격증명이 없으면 실행 가능한 어댑터·설정 검사·비교 도구까지 검증하고,
해당 업체의 실측은 미실행으로 기록한다.

### 현재 Proxy-Cheap + 실제 상주 워커

포함하지 않았다. 즉시 연속 요청하면 남은 최소 간격만큼 추가 대기가 생긴다.

### 비교와 실패도 포함한 기록

- 기존 운영 코드: 5회 중 4회 상품 수집, 성공한 검색 51.3~125.7초, 마지막 검색 challenge.
  `방충망 잠금장치` 입력에는 측정 스크립트 전달 과정에서 CR 1자가 섞였으므로 엄밀한 짝 비교에서 제외한다.
  baseline에는 저장/SSH 시간이 없으며 전후 순차 측정이므로 인과 효과나 통계적 A/B로 해석하지 않는다.
- 초기 개선판은 프록시 경로에서 44.7~60초 후 실패했다. 입력창만 빨리 뜬다고 준비 완료로
  간주한 가정을 철회했다. 워밍 시간만 복구한 시험도 실패했다. 기존 마우스/스크롤 워밍 동작까지
  보존한 뒤 2회 시험(33.9/5.2초) 및 위 상주 워커 5회 시험이 성공했다.
  출구 IP가 통제되지 않아 워밍 동작 하나의 인과 효과는 확정하지 않는다.
- 직결 비교는 5/5 성공, 첫 검색11.3초/후속2.3~3.0초였다. 진단용이며 운영 기본 경로는
  **현재 프록시 유지**다. 직결 전환은 자동으로 수행하지 않는다.
- 시크릿 검색 요청을 반영했다. 일반 Chrome 쿠키와 분리된 `Target.createBrowserContext`를
  사용하며 같은 검색용 시크릿 컨텍스트를 TTL 안에서 재사용한다. 매번 새 쿠키통으로 만드는
  방식과는 다르다. 컨텍스트 생존 중에는 검색 이력이 다음 결과에 영향을 줄 수 있다.
- 필수 데이터 계약(상품 필드/연관/자동완성)과 개수는 확인했다. 상품 순위·개인화의 불변성,
  장시간 유지·출구 IP 변경·혼잡 시간대, 실서비스 p95는 아직 확인하지 않았다.

Proxy-Cheap도 sticky 세션의 출구가 기기 이탈 때 바뀔 수 있고, 특정 사이트 수용을 보장하지
않는다고 명시한다. 다른 세션 ID가 다른 IP라는 가정은 제거했다.
[공식 FAQ](https://support.proxy-cheap.com/hc/en-us/articles/38182068823837-Proxy-Cheap-Frequently-Asked-Questions)
Zyte 어댑터는 `browserHtml`/`httpResponseBody` 문서에 맞춘 선택적 비교 경로다.
[공식 API](https://docs.zyte.com/zyte-api/usage/reference.html)

### 검증 및 남은 관문

- 핵심 오프라인 테스트 144개 통과(기존 단위/회귀/마켓 + 신규 지연/계약/실제 Unix 소켓).
- 웹 테스트 27개 통과(인증, 입력, SSH 프레이밍, 완료/실패 상태, 화면 계측 로그의 값 제한).
- 새 모듈 Ruff 검사 통과. 변경 diff 공백 검사 통과.
- 배포 shell 문법/plist 검사 통과. 실제 Chrome의 빈 시크릿 컨텍스트로
  `disposeOnDetach` 연결 종료 시 정리까지 확인했다(대상 사이트 요청 없음).
- UI는 실제 Chrome에서 자동완성 선표시, 상품 선표시, 도매꾹 실패 시 상품 보존,
  폴링의 추가 검색 금지, JavaScript 오류 없음 확인.
- 회귀 검사에서 기존 테스트의 전역 autocomplete 모의 함수가 복원되지 않던 문제를 발견해
  복원하도록 고쳤다. 워밍 쿠키 상태를 가정하던 컨텍스트 수명 테스트도 역할에 맞게 분리했다.
- 실서비스 웹→SSH→워커 경로와 GitHub CI는 운영 전환 전에 확인해야 한다.
  테스트 통과는 장기 차단 안정성이나 목표 p95 달성을 뜻하지 않는다.

## 실행·운영

설정 검사는 대상 사이트에 접속하지 않는다.

```sh
python cpk_benchmark.py --check
python cpk_benchmark.py --backend browser_reuse --queries-file state/latency-keywords.txt --output state/pilot.jsonl --limit 5
python cpk_benchmark.py --summarize state/pilot.jsonl
```

`alternate_proxy`는 별도 포트9224/프로필과 해당 공급사 자격증명 형식을 사용한다.
`zyte`는 키가 있어야 실행한다. 출력의 성공 계약과 실패율을 함께 비교하고 업체 비용은
대시보드 청구액으로 별도 기록한다. 현재 다른 업체를 결제하거나 계정을 만들지 않았다.

워커는 기본적으로 프록시를 사용하고 TTL은 480초(공급사 TTL 이내), 요청 마감은 대기열을
포함해60초다. 정리/저장/SSH는 별도 시간이 든다. 정상 세션만 재사용한다. 자동 주기 검색은
없고 유휴 시간에는 기존 CDP 이벤트만 처리한다. 429는 공통 중단한다. 프록시 challenge는
기존 마켓처럼 최대2회 시도하며, 직결 선택 시 challenge/403에서 공통 중단하고 재시도하지 않는다.
보조 HTTP 조회는 브라우저 탐색과 병렬이지만 중단·일일 예산에 포함한다.

로그 위치: 맥미니 `state/performance.jsonl`(request_id/단계/결과), Railway `cpk.timing`
(SSH/화면 표시). 상태 조회는 수집을 다시 시작하지 않는다. 작업 JSON은 디스크에 저장하며
재시작 때 7일 지난 작업을 정리하고, 미완료 작업을 재시작 실패로 바꾼다.

배포는 아직 하지 않았다. 저장소 `CLAUDE.md`의 외부 배포 사전 승인 규칙을 따른다.
승인 후 순서:

1. GitHub 변경 브랜치에서 오프라인 CI 통과를 확인한다. 메인 push는 Railway 자동 배포임에 주의한다.
2. 맥미니 기존 `cpk_*.py`, `deploy`를 별도 아카이브로 보관하고 SQLite backup API로 DB를 백업한다.
3. `deploy/push_to_mini.sh`로 코드만 전송한 후 `sh deploy/install_worker.sh`로 워커만 설치한다.
   `cpk.env` 자격증명과 Chrome 본체는 변경하지 않는다. 기본 `CPK_WORKER_ROUTE=proxy` 유지.
4. 로컬 소켓 health와 forced-command `__worker__` 시작/조회를 확인하고 웹 변경을 배포한다.
5. 웹에서 한 건을 제한 확인해 화면→SSH→워커의 동일 request_id와 필수 결과를 확인한다.
   배포 직후에는 실사용 성능/실패율을 관찰하고 목표 p95는 충분한 표본 이후 판단한다.

복구: Railway를 이전 배포로 되돌린 뒤 `launchctl bootout gui/$(id -u)/com.cpk.worker`로
워커를 종료하고 백업한 코드/래퍼를 복원한다. 추가한 SQLite 상태 컬럼은 이전 코드와 호환되므로
검색 결과를 지우거나 DB를 덮어쓰지 않는다. 자격증명·IP·예약 작업은 복구 과정에서도 변경하지 않는다.

## 0. 전제 — 테스트가 무엇이고 무엇이 아닌가

- **테스트 = 결함을 찾고 품질을 평가하는 활동 전체.** 실행만이 아니라 요구사항 검토·설계·데이터 준비·보고까지 포함한다.
- **검증(verification)과 확인(validation)을 둘 다 한다.** 검증 = "시킨 대로 만들었나". 확인 = "이게 사용자가 원한 것인가". 시킨 대로 만들어도 사용자 목적(수익·원금보존)에 안 맞으면 실패다.
- **테스트와 디버깅은 다른 활동이다.** 테스트가 실패를 드러내면, 디버깅은 재현 → 원인 찾기 → 고치기다. 고친 뒤에는 반드시 **확인 테스트**(그 실패가 사라졌나)와 **회귀 테스트**(다른 데가 깨지지 않았나)를 한다.
- **테스트 ≠ QA.** 테스트는 제품을 보는 사후 활동, QA는 과정을 보는 예방 활동이다. 사고가 나면 테스트를 추가하는 것으로 끝내지 말고 **어떤 과정 결함이 그 코드를 통과시켰는지**(리뷰 누락? 배포 절차?)를 함께 적는다.

### 0.1 일곱 원칙 (이 프로젝트의 실제 사례로)

| # | 원칙 | 이 프로젝트에서의 의미 |
|---|---|---|
| 1 | 테스트는 결함이 **있음**을 보이지 **없음**을 증명 못 한다 | "테스트 전부 통과"는 "버그 없음"이 아니다. 보고서에 "통과"만 쓰지 말고 **무엇을 안 봤는지**를 쓴다. |
| 2 | 전수 테스트는 불가능하다 | 기법(동등분할·경계값·결정표·상태전이)과 **위험 기반 우선순위**로 고른다. |
| 3 | 이른 테스트가 싸다 | PRD 단계에서 인수 기준을 테스트 문장으로 쓴다. 코드 뒤에 테스트를 붙이면 설계 결함을 못 잡는다. |
| 4 | 결함은 뭉쳐 있다 | 사고 이력이 있는 모듈(주문 전송·잔고 회계·워치독 배선·RPC 폴백)에 테스트를 더 준다. 메모리의 사고 목록이 위험 지도다. |
| 5 | 테스트는 닳는다 | 같은 회귀 스위트만 돌리면 새 결함을 못 잡는다. 사고마다 **새 테스트**를 추가하고, 탐색 세션을 주기적으로 한다. |
| 6 | 테스트는 맥락에 따라 다르다 | 리서치 스크립트와 실탄 봇의 요구 수준은 다르다. 실탄 봇은 §8의 추가 관문을 통과해야 한다. |
| 7 | 결함 없음의 오류 | 테스트 다 통과하고 배포한 봇이 8토큰 0승으로 끝날 수 있다(hoodsniper). 기능 검증과 **전략 검증**은 별개다. |

### 0.2 용어 (보고서에 이 뜻으로 쓴다)

- **오류(error)**: 사람이 저지른 실수. **결함(defect)**: 그 결과로 코드·문서에 남은 잘못. **실패(failure)**: 결함이 실행돼 드러난 잘못된 동작. **근본 원인(root cause)**: 그 오류가 나오게 만든 상황.
  - 예: "문자열 치환 패치로 `act()` 호출이 지워짐"(결함) → "2일간 매수 0건"(실패) → "패치 후 `run(once)` 경로 테스트가 없었음"(근본 원인).
- **테스트 기반(test basis)**: 테스트를 뽑아내는 근거 문서 = PRD·인수 기준·사용자 지시·과거 사고 메모리.
- **테스트 조건**: "무엇을 시험할지"의 한 항목. **테스트 케이스**: 전제조건·입력·기대 결과가 있는 실행 단위. **커버리지 항목**: 기법이 정의하는 "빠짐없이 밟아야 할 칸".
- **추적성(traceability)**: 요구사항 ↔ 테스트 조건 ↔ 테스트 케이스 ↔ 결과 ↔ 결함이 서로 연결되는 것. 테스트 이름에 요구사항·사고 날짜를 넣는 이유다.

## 1. 테스트 프로세스 — 작업마다 이 순서를 밟는다

ISTQB의 7활동을 이 프로젝트의 산출물로 번역한 것이다. 작은 작업은 각 단계가 한 줄이어도 되지만 **건너뛰지는 않는다.**

| 활동 | 이 프로젝트에서 하는 일 | 산출물 |
|---|---|---|
| 1. 계획 | 목표·범위·위험·어느 계층까지 돌릴지·완료 기준을 정한다 | PRD의 "테스트 계획" 절 (§6.1 템플릿) |
| 2. 모니터링·통제 | 진행하면서 계획과 어긋나면 조정한다 (예: 통합 환경 불가 → 대체 수단 명시) | 작업 중간 보고 |
| 3. 분석 | 테스트 기반에서 **테스트 조건 목록**을 뽑고 위험순으로 우선순위를 매긴다. 기반 문서의 모순·빈칸도 여기서 발견한다 | 테스트 조건 목록 (착수 전 합의) |
| 4. 설계 | 조건을 케이스로 구체화한다. 기법(§4)으로 커버리지 항목을 정하고, 필요한 데이터·환경(픽스처·DRY·아카이브 RPC)을 정한다 | 케이스 목록·픽스처 요구 |
| 5. 구현 | 테스트 코드·픽스처·스크립트를 만든다. 실행 순서(빠른 것 먼저, 위험 큰 것 먼저)를 정한다 | `test/` 트리 |
| 6. 실행 | 계층별로 돌리고 결과를 기록한다. 이상은 원인까지 분석한다 | 실행 로그·결함 보고 |
| 7. 완료 | 미해결 결함은 메모리/TRIAL_AND_ERROR에 남긴다. 재사용할 테스트웨어는 보존한다. 완료 보고서를 쓴다 | 완료 보고 (§6.5 템플릿) |

**분석 단계 규칙**: 조건 목록에는 요구사항에 안 보이는 아키텍처 조건을 반드시 넣는다 — 멱등성(같은 신호 두 번), 동시성(같은 지갑 동시 전송), 재시작(상태 파일 복원), 부분 실패(전송됐는데 영수증 못 받음), 시계(UTC/KST·에포크 경계), 외부 응답 0/빈값/429.

## 2. 테스트 레벨 — 다섯 층과 이 프로젝트의 대응

| ISTQB 레벨 | 여기서의 형태 | 언제 돌리나 | 무엇을 잡나 |
|---|---|---|---|
| 컴포넌트(단위) | `test/unit/` — 순수 함수·모듈 단독. 외부 없음 | 코드 변경마다 | 계산·파싱·분기·경계 |
| 컴포넌트 통합 | 모듈끼리 실제로 엮어 돌림 (watcher+ledger+executor, 대역은 외부 경계만) | 모듈 경계를 건드렸을 때 | 배선 누락·인터페이스 불일치 (`act()` 미호출 사고) |
| 시스템 | 리플레이 — 실제 과거 블록/로그를 전체 경로로 흘림, 전송만 차단 | 배포 전 1회, 사고 후 | 신호→행동 전 구간의 누락·오판 |
| 시스템 통합 | 실제 RPC·Kyber·거래소 API에 읽기 전용으로 붙임 (`live.test`) | 외부 스펙이 바뀌었을 가능성이 있을 때 | 외부 응답 형식 변화·429·지연 |
| 인수 | DRY 가동 → 소액 LIVE 카나리아 → 사용자 확인 | LIVE 전환 시 | "사용자가 원한 게 이것인가" |

- 레벨마다 **목적이 다르다**. 단위 테스트가 많다고 통합을 생략하지 않는다 (배선 사고는 단위로 못 잡는다).
- 각 레벨의 **진입 기준**: 아래 레벨이 초록불. **완료 기준**: 그 레벨의 커버리지 항목이 전부 밟혔고 미해결 결함이 기록됨.

### 2.1 테스트 타입

- **기능**: 명세대로 동작하나. **비기능**: 얼마나 잘 동작하나 — 이 프로젝트에서 실제로 중요한 것은 **신뢰성**(재시작·RPC 장애·429 후 복구), **성능**(신호→전송 지연, 틱 시간), **보안**(키가 로그·채팅·아카이브에 새지 않나), **유지보수성**(미러 값 4곳 동기화).
- **블랙박스**: 명세에서 뽑는다. 구현이 바뀌어도 살아남는다. **화이트박스**: 코드 구조에서 뽑는다. 명세가 빈약할 때 강하고, "빠진 요구사항"은 못 잡는다. 둘 다 쓴다.
- **확인 테스트 vs 회귀 테스트**: 수정 후 (a) 그 실패를 재현하던 테스트가 통과하는지, (b) 스위트 전체가 그대로 통과하는지. 둘 다 보고에 쓴다. 회귀는 자동화 대상 1순위다 (서버 타이머 회귀 스위트).

### 2.2 유지보수 테스트 — 운영 중 변경의 트리거 3종

1. **수정**(핫픽스·개선): 영향 분석 먼저 — 어떤 모듈·감시·미러 값이 연결돼 있나. 배포 전 **라이브 코드와 md5 대조**(다른 세션의 수정을 덮어쓰는 사고 방지).
2. **환경 변경**(RPC 교체·Node 버전·API 버전·정산 방식 전환): 새 환경에서 스위트 재실행. 서버 Node 버전으로 한 번 더 돌린다.
3. **폐기**(봇 아카이빙): 아카이브 무결성(md5)·복원 가능성·감시 배선 제거를 테스트한다. 유닛 이관이 다른 워치독을 깨뜨린 사고가 있다.

## 3. 정적 테스트 — 실행 없이 잡는 것

실행 전에 읽어서 잡는 결함이 가장 싸다. 이 프로젝트에서 정적 테스트는 다음 세 가지다.

1. **리뷰 (PRD·코드·유닛 파일·배포 스크립트)**
   - 착수 전 PRD 리뷰: 모순·모호·빠짐·중복을 찾아 **질문으로** 되돌린다 (추측해서 채우지 않는다).
   - 배포 전 코드 리뷰: 변경 diff 전체를 다시 읽는다. 특히 **문자열 치환·정규식 패치는 결과물을 눈으로 확인**한다.
   - 리뷰 관점 체크리스트(§4.6)를 쓴다. 체크리스트는 사고 때마다 갱신하고, 너무 길어지면 자동화 가능한 항목을 테스트로 옮긴다.
2. **정적 분석(도구)**: 린트·타입·죽은 코드·미사용 변수. CI/타이머에 넣을 수 있으면 넣는다.
3. **라이브 대조**: 배포 대상 서버의 현재 파일·유닛·env 키 목록과 로컬을 대조한다. "값"이 아니라 "지문(md5)"으로 본다.

정적 테스트가 잘 잡는 것: 요구사항 모순, 인터페이스 불일치(파라미터 개수·순서), 도달 불가 코드, 표준 위반, 테스트 기반 커버리지 구멍(인수 기준에 대응 테스트 없음).
정적 테스트로 못 잡는 것: 데이터 의존 실패(0으로 나눔), 타이밍, 외부 응답 변화 → 동적 테스트가 필요하다.

## 4. 테스트 기법 — 케이스를 "체계적으로 적게" 뽑는 법

기법은 "무엇을 시험할지"(분석)와 "어떻게 시험할지"(설계)를 돕는다. 아래 중 **4.1~4.4는 해당 구조가 코드에 있으면 의무 적용**이다.

### 4.1 동등 분할 (Equivalence Partitioning)

- 같은 방식으로 처리될 입력을 한 칸으로 묶고, **칸마다 최소 1개** 값을 시험한다. 유효 칸과 **무효 칸** 둘 다.
- 칸은 겹치지 않고 비어 있지 않아야 한다. 입력뿐 아니라 출력·설정값·내부 상태·시간·외부 응답에도 적용한다.
- 무효 칸은 **한 케이스에 하나만** 넣는다 (둘 넣으면 한 결함이 다른 결함을 가린다).
- 파라미터가 여럿이면 최소 기준은 **Each Choice** — 각 파라미터의 각 칸이 한 번 이상 등장. 조합은 결정표(4.3)로 간다.
- 예: 미러 매도 비율 = {B가 전량 매도, 일부 매도, 먼지 이하 매도, 매도 0, 보유보다 많이 매도(비정상)}.

### 4.2 경계값 분석 (Boundary Value Analysis) — **모든 임계값 파라미터에 3값 BVA 의무**

- 순서가 있는 칸의 **양 끝**이 경계다. 결함은 경계가 한 칸 어긋나거나 빠진 데서 나온다.
- **2값 BVA**: 경계값 + 옆 칸의 이웃. **3값 BVA**: 경계값 + 양쪽 이웃. `x ≤ 10`을 `x == 10`으로 잘못 짠 결함은 3값(9, 10, 11)이어야 잡힌다.
- 이 프로젝트의 `*_MIN`/`*_MAX`/창(`WIN_LO`/`WIN_HI`)/τ/캡/먼지 비율/슬리피지는 전부 경계다. **각 경계에 3값 테스트가 없으면 완료가 아니다.**
- 경계는 숫자만이 아니다: 빈 목록/1개/많음, 블록 창 시작/끝, 에포크 경계 초, 잔고 = 가스예비금 정확히, 0 이하 금액, 최대 정밀도(18 decimals vs 6 decimals).
- 특히 **부동소수·정수 단위 혼합**(USDG 6dec, NET 18dec, wei) 경계에서 반올림 방향을 명시적으로 시험한다.

### 4.3 결정표 (Decision Table) — **게이트·조건 조합에 의무**

- 조건들이 조합돼 행동을 결정하는 로직(진입 게이트, 발사 허용, 알림 등급)은 **전체 조합 표**를 먼저 쓴다. 조건은 행, 규칙은 열. `T/F/–(무관)/N/A(불가능)`.
- 커버리지 항목 = **실현 가능한 열 전부**. 불가능한 조합은 삭제하고, 무관 조건은 병합해 표를 줄인다.
- 표를 쓰는 과정 자체가 요구사항의 **빈칸·모순**을 드러낸다(예: "잔고 부족 && 라우트 없음"일 때 어떤 원장 상태를 남기나). 빈칸은 코딩 전에 질문한다.
- 예 (hoodsniper 매수 게이트):

  | 조건 | R1 | R2 | R3 | R4 | R5 |
  |---|---|---|---|---|---|
  | 이미 매수(ok/dry) | T | F | F | F | F |
  | 진행중 락 | – | T | F | F | F |
  | 잔고 ≥ 금액+예비 | – | – | F | T | T |
  | 라우트 있음 | – | – | – | F | T |
  | **행동** | 무시 | 무시 | nobalance | noroute | 전송 |

### 4.4 상태 전이 (State Transition) — **수명주기가 있는 객체에 의무**

- 상태·이벤트·전이·가드·행동을 그린다. 상태표로 바꾸면 **무효 전이(빈 칸)** 가 드러난다.
- 커버리지 3단계: 모든 상태 < **모든 유효 전이(0-switch, 기본 요구)** < 모든 전이(무효 전이 시도 포함, 실탄 경로엔 이걸 요구).
- 무효 전이는 케이스당 하나만 시도한다.
- 이 프로젝트의 상태 기계: 포지션(없음→진행중→보유→매도중→청산), 주문(요청→전송→영수증 대기→확정/revert/unknown), 봇 서비스(가동→정지→mask), 세션 쿠키(유효→만료→재발급), RPC(정상→느림→죽음→교체).
- "unknown"(전송됐을 수 있음) 상태에서의 전이를 빼먹는 것이 사고 단골이다. 반드시 넣는다.

### 4.5 화이트박스 — 구문·분기 커버리지

- **구문 커버리지**: 모든 실행문이 한 번은 실행됨. **분기 커버리지**: 모든 if/switch/루프 탈출의 양쪽이 실행됨. 분기 100%는 구문 100%를 포함한다(역은 아님).
- 실탄 경로(전송·잔고·원장 기록·알림 분기)는 **분기 100%** 를 목표로 한다. 리서치 스크립트는 요구하지 않는다.
- 분기를 다 밟아도 **경로·데이터 의존 결함**은 남는다. 화이트박스는 "빠진 요구사항"을 못 잡으므로 블랙박스와 함께 쓴다.
- 화이트박스는 실행 전 **코드 드라이런(머릿속 실행)** 에도 쓴다. 패치 후 "이 신호가 들어오면 어느 줄을 지나 어디서 전송되나"를 손으로 따라간다.

### 4.6 경험 기반 — 오류 추측·탐색·체크리스트

**오류 추측 / 결함 공격 목록** (이 프로젝트의 실제 사고에서 뽑음. 새 사고마다 추가한다):

- 조용한 0: 실패가 0/빈값/빈 배열로 위장 → "0건"은 관측 여부·거래일·매처 3단 확인 없이는 결과가 아니다.
- 배선 누락: 탐지는 되는데 행동 함수가 호출되지 않음 → 신호→행동 끝까지 가는 `run(once)` 테스트.
- 동시성·nonce: 같은 지갑 동시 전송, 같은 토큰 동시 매도 → 직렬화·재확인 테스트.
- 미러 값 불일치: 상수를 복사해 둔 감시·알림·문서 중 하나만 바뀜 → 지문 검사.
- 단위 혼합: 6dec/18dec/wei, USD/ETH/NET 섞인 합산.
- 재시작: 상태 파일이 없거나 반쯤 써졌을 때, 비원자적 쓰기 레이스(하트비트 epoch 오경보).
- 외부 응답 변화: 429·403·빈 body·필드명 변경·정산 방식 전환.
- 시계: UTC/KST 혼동, 에포크 경계, 일 캡의 "하루" 정의.
- 라운딩 방향: 패시브 주문이 되려면 어느 쪽으로 내림/올림해야 하나.
- 대역(mock)이 실제와 다름: 테스트는 초록, 운영에서 붉음 → 실제 픽스처(온체인 영수증·실제 API 응답 저장본)를 우선한다.
- 배포가 승인값을 덮어씀: 옛 사본 위에 픽스 배포.
- 키 유출: 로그·알림 본문·아카이브·채팅에 키/시드가 찍히나.
- 워치독이 죽은 것을 감시: 대상이 없어졌는데 경보만 남음, 혹은 대상이 바뀌었는데 개수만 셈.
- 시계 두 개: 우리 벽시계와 상대(시퀀서·거래소) 시계는 다르다. 발사 시각은 상대 시계로 실측해 보정하고(블록 timestamp 관측), 이르면 revert·늦으면 경쟁에 진다 (2026-09-17 민팅봇: 시퀀서 지연 0.09~0.15s 실측).
- 서명 뒤 조건이 바뀜: 미리 서명·준비해 둔 뒤 일정·가격·한도가 바뀌면 준비물이 독이 된다. 발사 직전까지 재확인하고, 두 번째 변경도 본다 (09-17: 서명 후 연기 → 44건 revert, 감시 스레드가 0.3초 전 종료 → 2차 연기 못 봄).
- 대역 서버의 직렬화 아티팩트: 가짜 외부 서버가 한 프로세스라 요청을 줄 세우면 "봇이 느리다"로 오판한다. 클라이언트 쪽 시각(소켓에 쓴 시각)을 따로 재고, 실제 서비스로 최종 확인한다 (09-17: 가짜 RPC 2초 퍼짐 vs 실제 시퀀서 18ms).
- 스레드 병렬≠동시: 파이썬 스레드 N개가 각자 보내면 GIL 때문에 줄을 선다. 동시 발사는 한 스레드가 미리 연 연결에 연속 쓰기(volley)로 한다.
- 공급이 먼저 사라짐: 선착순 이벤트는 우리 차례 전에 다른 단계(허용목록·소유자 서명 민팅)가 물량을 다 가져갈 수 있다. "잔여"를 시작 직전까지 감시하고, 0이면 설계된 정지로 끝난다는 것을 사용자에게 미리 알린다 (09-17 20:52: 공개 2시간 전 소유자가 잔여 48 전량 민팅 → 발사 0·손실 0).
- 부하 중 시간 민감 테스트: 같은 서버에서 부하 테스트를 돌리는 동안 단위 스위트를 돌리면 시간 기준(0.1s) 단언이 우연히 깨진다. 부하 테스트와 단위 스위트는 겹치지 않게 돌리고, 실패 시 테스트 이름이 남도록 배포 스크립트가 마지막 줄만 잘라 보이지 않게 한다.
- 배포 스크립트가 실패를 삼킴: `unittest | tail -1 && restart`는 tail이 성공이라 테스트가 실패해도 재시작한다. `set -o pipefail`로 실패 시 중단 (09-17 실제 발생, 가드가 있어 지문 불일치는 잡았음).
- 승인값이 실효값이 아님: 승인받은 숫자가 설정 파일에는 있는데 실제 동작(서명된 바이트·전송된 주문)에는 다른 값이 들어간다. 상한을 "자르는 용도"로만 쓰는 공식에서 생긴다. 설정 파일의 숫자를 대조하는 테스트로는 못 잡는다 → **효력이 나는 곳에서 읽어 단언**(서명 바이트 파싱·저널·로그)하고, 프로그램이 시작할 때 "실제로 쓸 값 vs 승인값"을 찍게 한다 (2026-09-18 민팅봇: 천장 40 gwei 승인, 실제 서명 1 gwei — 4개 대상 동안 미발견, 기본수수료 급등 시 0/44).
- 긴 창에서 안 끝나는 마감: "이벤트 종료 시각+α"에 기대는 대기·재시작 조건은 창이 1시간→3일·30일로 바뀌면 사실상 무한이 된다. 창 길이를 바꿔 가며 시험한다 (09-18: 영수증 대기·감시 재시작).
- 대역 서버 자원 충돌: 가짜 서버가 고정 포트를 쓰면 동시에 도는 다른 작업의 가짜 서버에 붙어 **그럴듯한 가짜 결과**가 나온다. 빈 포트 선택 + 기동 실패 시 결과 없이 중단 (09-18: 남의 가짜 체인 결과 1/44 를 내 결과로 읽을 뻔함).

**탐색 테스트**: 명세가 빈약하거나 새 외부 시스템을 처음 붙일 때. **시간을 정하고(예: 30분) 차터(목표)를 적고** 시작한다. 설계·실행·평가를 동시에 하며 발견한 것을 세션 시트에 적고, 끝나면 정식 테스트로 옮길 것을 고른다. 탐색 세션에서 경계값·동등분할을 즉석에서 쓴다.

**체크리스트 테스트**: 리뷰·배포·폐기에 쓴다. 항목은 질문형·개별 확인 가능해야 하고, 자동화 가능한 항목은 체크리스트에서 빼고 테스트로 옮긴다. 사고 분석 때마다 갱신하되 길어지지 않게 유지한다. (§9)

### 4.7 협업 기반 — 인수 기준과 ATDD

- 사용자 요청은 사용자 스토리로 읽는다: "[역할]로서 [목표]를 원한다, [가치] 때문에". INVEST(독립·협상가능·가치·추정가능·작음·**테스트가능**)에서 "테스트 방법을 모르겠다"면 스토리가 불명확하거나 가치가 없다는 신호 → 질문한다.
- **인수 기준**은 PRD에 두 형식 중 하나로 쓴다: 시나리오형(Given/When/Then) 또는 규칙형(입력→출력 표). 긍정 시나리오 → 부정 시나리오 → 비기능 순서로.
- **ATDD**: 인수 기준을 먼저 테스트 문장으로 쓰고, 그 다음 코드를 만든다. 테스트는 스토리의 모든 특성을 덮되 넘어가지 않고, 두 테스트가 같은 특성을 중복 검증하지 않는다.
- 테스트 우선(Red→Green→Refactor)은 조건부다: 목표가 명확하고 검증 가능하면 적용, 탐색·비결정적 의존·레거시면 생략하고 **"생략+이유+대신 무엇으로 확인"** 을 보고한다.

## 5. 자동화·도구

- 회귀·반복 비교·커버리지 측정은 자동화한다. 사람 판단(전략 타당성·사용자 의도 확인)은 자동화하지 않는다.
- 자동화의 위험: 도구 과신(초록불 = 안전 착각), 유지비 과소평가, 대역이 실제와 멀어짐, 도구 호환(서버 Node 18 vs 로컬 23 — 서버 버전으로도 돌린다).
- **변이 검증**을 습관화한다: 테스트가 정말 잡는지 확인하려고 코드에 고의 결함(경계 한 칸, 조건 반전, 호출 삭제)을 넣고 붉은불이 켜지는지 본다. 붉어지지 않는 테스트는 테스트가 아니다. 보고에 "변이 n/n"으로 쓴다.
- 픽스처는 **실제 데이터 저장본**(온체인 영수증·API 응답)을 우선한다. 손으로 지은 대역은 외부 경계에서만.
- 테스트 이름에 **요구사항 또는 사고 날짜**를 넣어 추적성을 만든다. 예: `"사전 시뮬 revert면 전송하지 않는다 (09-14 가스낭비 회귀)"`.
- 반복 데이터는 for 루프가 아니라 파라미터라이즈드 테스트로 쓴다. 루프는 어느 케이스가 깨졌는지 못 알려주고 뒤 케이스를 실행하지 않는다.

## 6. 관리 — 계획·위험·보고·형상·결함

### 6.1 테스트 계획 (PRD 안의 한 절, 5~15줄)

```
테스트 계획
- 범위/목표: 무엇을 어느 수준까지 (실탄 경로 분기 100%, 리서치는 산출물 검증만)
- 테스트 기반: PRD §n, 사용자 지시 "…", 사고 메모리 […]
- 위험 상위 3: (가능성×영향) → 각각 대응 테스트
- 레벨/타입: 단위·통합·리플레이·live·DRY·카나리아 중 무엇을 언제
- 기법: 경계 목록(3값 BVA 대상), 결정표 대상 게이트, 상태기계 대상
- 진입/완료 기준: DoR = 인수 기준 확정·픽스처 확보 / DoD = 전 레벨 초록·변이 n/n·미해결 결함 기록
- 환경/데이터: 아카이브 RPC, 픽스처 파일, 서버 Node 버전
- 생략 항목과 이유
```

### 6.2 진입·완료 기준

- **진입(DoR)**: 인수 기준이 테스트 가능한 문장으로 있음, 경계 조건 질문이 답변됨, 테스트 데이터/환경이 있음, 이전 레벨 초록.
- **완료(DoD)**: 계획한 커버리지 항목 전부 실행, 실패 0 또는 실패 전부 결함 기록, 회귀 스위트 자동화됨, 실탄이면 §8 관문 통과.
- 시간·예산 소진도 완료 사유가 될 수 있으나, 그때는 **남은 위험을 사용자에게 보고하고 승인**을 받는다. 스스로 축소하지 않는다.

### 6.3 우선순위·견적

- 실행 순서 = **위험 기반** 우선(돈이 나가는 경로 먼저) → 커버리지 기반(많이 밟는 것 먼저) → 요구사항 우선순위. 의존 관계가 있으면 선행 테스트를 먼저.
- 견적은 3점 추정 `E=(a+4m+b)/6`, 오차 `(b−a)/6` 으로 말한다. "테스트에 얼마 걸리나"에 한 숫자로 답하지 않는다.

### 6.4 테스트 피라미드·사분면 (이 프로젝트 판)

```
        [카나리아 LIVE 소액]      ← 적게, 느림, 사용자 승인 필요
       [DRY 가동 스모크]
      [live.test 외부 읽기전용]
     [리플레이 (실제 블록 전체 경로)]
    [통합 (모듈 배선)]
  [단위 (순수 함수·경계·결정표)]      ← 많이, 빠름, 매 변경마다
```

- Q1 기술·지원(단위·통합, 자동, 매 변경) · Q2 비즈니스·지원(인수 기준 예시, 리플레이) · Q3 비즈니스·비평(탐색·사용자 확인) · Q4 기술·비평(스모크·성능·복구). 네 칸이 다 있는지 계획에서 확인한다.

### 6.5 위험 관리

- 위험 = 가능성 × 영향. **제품 위험**(돈 잃음·나체 포지션·키 유출·조용한 정지)과 **프로젝트 위험**(외부 API 변경·서버 자원·시간)을 나눠 적는다.
- 위험 분석 결과가 테스트 범위·기법·커버리지·순서를 정한다. 사고 이력이 있는 영역은 가능성을 높게 잡는다.
- 대응: 테스트로 완화 / 수용(사용자 승인) / 이전(DRY·소액) / 비상계획(워치독·자동 정지). 무엇을 골랐는지 계획에 쓴다.
- 위험 모니터링: 워치독·타이머 회귀 스위트·일일 감사가 그것이다. 새 봇에는 이 세 가지가 있어야 인수 완료다.

### 6.6 모니터링·보고 — 완료 보고 형식 (의무)

```
테스트 결과
| 계층 | 실행 | 통과/실패 | 비고 |
| 단위 | ✅ | 42/0 (신규 3) | 변이 3/3 |
| 통합/리플레이 | ✅ | 13/0 | 실제 블록 12건 |
| live(외부) | ⏭ 생략 | – | 외부 경계 미변경 |
| 서버 환경 | ✅ | 42/0 | Node 18 |
- 커버리지: 경계 3값 BVA n/n 경계, 결정표 n/n 열, 상태전이 n/n 전이
- 확인 테스트: [실패 재현 테스트] 통과 / 회귀: 전체 통과
- 미해결·남은 위험: …
- 이번 작업에서 보지 않은 것: …
```

- 지표는 진행(실행/미실행), 결과(통과/실패), 결함(발견/수정), 커버리지, 위험(잔여)으로 나눠 쓴다. "통과"만 쓴 보고는 미완이다.
- 실패는 실패라고 쓴다. 출력과 함께. 건너뛴 것은 건너뛰었다고 쓴다.

### 6.7 형상 관리

- 테스트 코드·픽스처·기대값은 코드와 같은 버전으로 관리한다. 픽스처가 어느 블록·어느 API 버전에서 왔는지 파일 안에 적는다.
- 배포 단위(코드+env+유닛+감시)를 하나의 기준선(baseline)으로 본다. 기준선 변경은 승인 경위와 함께 메모리에 남긴다.
- 라이브와 로컬의 **지문 대조**가 형상 관리의 최소 실행이다.

### 6.8 결함 보고 (메모리·TRIAL_AND_ERROR에 남기는 형식)

```
- 제목: 한 줄 요약 (증상 + 위치)
- 발견 일시·발견 경로(어느 테스트/감시/사용자 알림)
- 대상: 봇/모듈/버전(md5)/환경(서버·Node)
- 재현: 최소 단계·입력·픽스처
- 기대 vs 실제 (로그 발췌)
- 심각도(돈·정지·오경보) / 우선순위
- 원인(결함) / 근본 원인(과정) / 수정 / 확인 테스트 이름
- 상태: 열림·수정됨·확인됨·기각(오탐)
```

- 이상(anomaly)이 전부 결함은 아니다. 오탐·변경 요청으로 판명되면 그렇게 적고 닫는다. 정적 분석의 지적도 같은 흐름으로 다룬다.

## 7. 테스트 작성 규칙 (금지·권장)

- private 메서드·내부 클래스를 직접 테스트하지 않는다. 공개 API로만.
- Mock을 최소화한다. 대역은 외부 경계(RPC·HTTP·시계·키)에만. 내부 모듈은 실제로 엮는다.
- 상태 검증(무엇을 반환·기록하는가)을 행위 검증(어떤 순서로 무엇을 불렀나)보다 우선한다.
- 반복 데이터는 파라미터라이즈드. 무효 입력은 케이스당 하나.
- public API가 다 테스트되는데도 불안한 private 코드는 필요 없는 코드일 수 있다. 지워보고 돌린다.
- 테스트가 비결정적(시간·네트워크)이면 시계·네트워크를 주입해 결정적으로 만든다. 그래도 안 되면 통합 계층으로 올리고 단위에서는 뺀다.
- 테스트는 실패 이유를 메시지로 말해야 한다. `assert.equal(a, b, "두 tx가 서로 다른 nonce를 써야 함")`.

## 8. 실탄 코드 추가 관문 (돈이 나가는 경로에만 적용)

1. **전송 경로 분기 100%** + 결정표 전 열 + 상태전이 전 전이(무효 포함).
2. **변이 검증** 통과: 최소 3종(경계 한 칸, 조건 반전, 전송 호출 삭제)에서 붉은불.
3. **DRY 스모크**: 실제 신호로 전송 직전까지 도달, 로그에 계획이 찍힘. "틱은 도는데 아무것도 안 하는" 실패 모드를 하트비트만으로 판단하지 않는다.
4. **워치독·회귀 타이머·일일 감사** 배선 완료 — 감시는 개수가 아니라 **대상**으로.
5. **배포 전 라이브 지문 대조**, 배포 후 **확인 테스트**(서버 환경에서 스위트 재실행 + 첫 신호 처리 로그 확인).
6. **파라미터 변경 없음** 또는 승인 경위 메모리 기록 (CLAUDE.md 절대 지침).
7. 키·시드가 로그·알림·아카이브·채팅에 없음.
8. 첫 LIVE는 소액 카나리아, 결과를 사용자에게 보고한 뒤 확대.

## 8.1 1회성 이벤트(민팅·런치·선착순) 추가 관문 — 2026-09-17 RareFriends에서 확립

카나리아(소액 실탄 반복)가 불가능한 한 방짜리 이벤트는 아래로 대신한다.

1. **가짜 외부 서비스 매트릭스**(stress/): 요청 한도(rps 25/30/60/100)·지연(20/200/500ms)·오류율(10/20/30%)·경쟁 소진(초당 10/40개)·매진·잔고 부족·일정 연기(서명 전/후)·외부 입구 다운. 결과표에 **첫 발사 시각·클라이언트 쓰기 시각·요청 폭주(rps)·429·revert·재발사**를 같이 싣는다. 전후 비교(v1 vs v2)는 같은 표로.
2. **외부 한도 실측**은 실전 IP가 아닌 버릴 수 있는 IP(다른 서버)에서 가짜 페이로드로 잰다. 실전 IP에서는 실제 발사 패턴(예: 44건 일제사격)만 재현해 통과를 확인한다.
3. **실체인 드레스 리허설**(rehearsal 스위치): 가짜 시작 시각을 잡고 실제 봇 코드로 실제 트랜잭션(0원 자기전송)을 쏴서 **어느 블록(timestamp)에 들어갔는지**를 판정 기준으로 삼는다. 리허설 중 프로세스 강제 재시작을 한 번 넣어 저널 복구도 본다. 스위치 기본값 off를 테스트로 고정한다.
4. **트리거 시각 3중 대조**: 체인 값(RPC 2곳)·운영자 화면 원본 데이터·봇 설정이 초 단위까지 같은지. 화면 표시는 분 단위로 반올림될 수 있다.
5. **과거 이벤트 재구성**: 같은 계약의 이전 단계 로그로 "시작 후 몇 초에 몇 개가 나갔나·시도 대 성공·건당 실비"를 뽑아 경쟁 강도와 비용 상한을 근거로 잡는다 (getLogs topic은 0x 접두어).
6. **동결 시각**: 이벤트 1시간 전부터 어떤 변경도 하지 않는다. 그 전까지 배포는 지문 대조 → 백업 → 서버 스위트 → 재시작 → 대기 로그 확인 순.
7. **관제**: 로컬에서 카운트다운+원격 로그 스트림(읽기 전용)을 띄우고, 결과는 폰 알림으로. 관제가 봇 자원과 경쟁하지 않는지 확인한다.

# 코딩 기본 지침 (전체본 · 보관용)

현재 적용 중인 것은 루트 `CLAUDE.md`의 핵심축이다.
이 문서는 리뷰 기준 / 확장 후보로 보관한다.

출처: TDD 강의(이규원) 중 '변하지 않는 가치'에 해당하는 부분.
핵심 전제 — 엔지니어링은 트레이드오프이며, 보편적으로 옳은 코드 기준은 없다.
작업마다 요구되는 수준이 다르다. 아래 항목은 규칙이 아니라 판단 재료다.

---

## A. 착수 전 (가장 비싼 자원은 코드 작성이다)

**A1.** 목표를 먼저 한 줄로 쓴다: "이 작업은 어떤 문제를 푸는가."
구현 수단이 아니라 목적을 쓴다.

**A2.** 요구사항의 빈칸을 찾아 **코딩 전에 질문한다.**
특히 경계: 입력이 0개일 때 / 1개일 때 / 비정상일 때 / 중복일 때.
추측해서 채우지 않는다. 모호한 채로 짠 코드는 나중에 버그로 돌아온다.
→ 한 번에 맞는 구현이 나오느냐를 결정하는 항목은 사실상 이것 하나다.

**A3.** 달성해야 할 목표를 테스트 케이스 목록으로 나열하고 합의한 뒤 착수한다.
요구사항에서 안 보이는 항목(멱등성, 동시성, 로깅 등 아키텍처 요구)도
이 단계에서 함께 도출해 목록에 넣는다.

**A4.** **변경 가능성이 높거나 결정이 어려운 것들의 목록을 먼저 적는다.**
(외부 API 스펙, 저장소 종류, 정책 상수, 포맷 등)
→ 이 목록에 있는 것들은 모듈 내부에 숨긴다. 이것이 설계의 출발점이다. (Parnas, 1971)

---

## B. 설계 (테스트가 통과해도 이것들은 자동으로 해결되지 않는다)

**B1.** 인터페이스는 "무엇", 구현은 "어떻게". 공개 API에 구현 사정을 노출하지 않는다.
A4 목록의 항목이 공개 API에 드러나 있으면 설계가 잘못된 것이다.

**B2.** **기존 코드베이스를 먼저 조사하고 그 용어·패턴·파라미터 순서를 따른다.**
같은 개념에는 이미 쓰이는 하나의 용어를 쓴다. 새 이름을 지어내지 않는다.
조사 없이 새로 만든 이름/구조가 있으면 그 이유를 보고한다.

**B3.** 재사용할 때는 **기존 코드를 수정하지 않는 방법을 최우선으로** 고려한다.
작은 수정이라도 연결된 코드에 어떤 여파를 줄지 예측하기 어렵다.

**B4.** 적응력으로 판정한다: "요구사항이 한 번 더 바뀌면 기존 코드를 고쳐야 하나, 추가/교체로 끝나나?"
후자가 되도록 설계한다.
단, **A4 목록에 오른 축에 대해서만** 추상화한다.
변하지 않을 것에 미리 추상화를 넣는 것은 오버엔지니어링이다.

**B5.** 켄트백 4규칙 우선순위를 따른다:
`테스트 통과 > (의도 노출 = 중복 제거) > 최소 요소`
- 의도 노출과 중복 제거는 **동순위**다. 충돌하면 판단하고, 왜 그렇게 택했는지 밝힌다.
- 중복 제거를 위해 의도가 흐려지는 추상화는 하지 않는다.
- 필요 없는 코드는 지운다.

**B6.** 응집도를 명시적으로 점검한다: 함께 바뀌는 것은 함께 둔다.
한 파일/함수가 여러 이유로 바뀌고 있으면 책임을 분리한다.
테스트는 이 문제에 대해 절대 경고해주지 않는다.

**B7.** **"테스트하기 어렵다"는 설계 신호로 취급한다.**
Mock을 여러 개 세워야 테스트가 되면, 테스트 기법을 고민하기 전에 의존 구조를 먼저 의심한다.
코드의 적응력이 높을수록 테스트 용이성도 함께 올라간다.

**B8.** 보편적 "클린 코드"를 목표로 삼지 않는다. 이 작업에 요구되는 수준을 맞춘다.
무엇과 무엇을 맞바꿨는지 말할 수 있어야 한다.

## C. 구현 · 테스트

테스트 세부는 `.claude/testing-guidelines-generic.md`(범용)·`.claude/testing-guidelines.md`(트레이딩 부록)로 이관했다. 아래 C3~C5는 그 요약이다.

**C1.** 최소한만 쓴다. 지금 요구사항을 만족시키는 데 필요 없는 코드는 넣지 않는다.
테스트되지 않은 코드는 나중에 어떤 부작용을 낼지 예측할 수 없다.

**C2.** 리팩터링은 **의미를 바꾸지 않고 구조만** 바꾸는 것이다.
- 테스트가 초록불인 상태를 유지하며 진행하고, 깨지면 되돌린다.
- 공개 인터페이스를 바꿔야 한다면 그건 리팩터링이 아니다. 별도로 보고한다.
- 검증 수단 없이 "정리했다"고 하지 않는다.

**C3.** 테스트 작성 금지 사항
- private 메서드/내부 클래스를 직접 테스트하지 않는다. 공개 API로만 테스트한다.
- Mock을 최소화한다. 대역이 늘수록 "테스트는 통과하는데 운영에서 깨지는" 가정이 커지고,
  내부 구현에 결합되어 리팩터링을 막는다.
- 상태 검증(무엇을 반환하는가)을 행위 검증(어떻게 만드는가)보다 우선한다.
- 반복 데이터는 for 루프가 아니라 파라미터라이즈드 테스트로 쓴다.
  루프는 어느 케이스가 깨졌는지 못 알려주고 뒤 케이스를 실행하지 않는다.
- public API가 전부 테스트되는데도 불안한 private 코드가 있으면,
  그건 필요 없는 코드일 수 있다. 지워보고 테스트를 돌린다.

**C4.** 테스트 실행 계층 (매번 전부 돌리지 않는다)
- 단위: 코드 변경마다 — 빠르고 피드백 품질 높음
- 통합: 모듈 경계를 건드렸을 때
- 전수/인수: 작업 완료 보고 직전 1회 — 느리고 피드백 품질 낮음
- 어느 계층을 돌렸고 무엇을 생략했는지 결과 보고에 명시한다.

**C5.** 테스트 우선 작성(Red→Green→Refactor)은 **조건부로** 적용한다.
- 적용: 목표가 명확하고 검증 가능하며 기존 테스트가 있는 경우
- 미적용: 탐색적 작업 / 비결정적·느린 의존성 / 테스트 없는 레거시
- 미적용 시 "생략했음 + 이유 + 대신 무엇으로 확인했는지"를 반드시 보고한다.
- 안 맞는 환경에 무리하게 적용하면 비용만 늘고 TDD 자체를 오해하게 된다.

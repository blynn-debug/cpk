# 테스트 지침 — 범용본 (프로젝트 무관)

루트 `CLAUDE.md`의 "테스트" 절이 핵심축이고, 이 문서는 그 근거·세부·템플릿이다.
출처: ISTQB Certified Tester Foundation Level Syllabus v4.0.1 (2024-09-15).
개발자와 테스터가 같은 사람(또는 같은 에이전트)인 소규모 프로젝트를 전제로 옮겼다.
"한다/하지 않는다"는 규칙, "고려한다"는 판단 재료다.
도메인 특화 사례(사고 목록·실탄 관문)는 프로젝트별 부록 파일에 둔다. 이 문서에는 넣지 않는다.

## 0. 전제

### 0.1 테스트란

- **결함을 찾고 품질을 평가하는 활동 전체**다. 실행만이 아니라 요구사항 검토, 설계, 데이터 준비, 보고를 포함한다.
- **검증(verification)** = 명세대로 만들었나. **확인(validation)** = 사용자가 원한 것인가. 둘 다 한다. 명세대로 만들어도 목적에 안 맞으면 실패다.
- **테스트 ≠ 디버깅.** 테스트가 실패를 드러내면 디버깅은 재현 → 원인 찾기 → 고치기다. 고친 뒤에는 **확인 테스트**(그 실패가 사라졌나)와 **회귀 테스트**(다른 곳이 깨지지 않았나)를 둘 다 한다.
- **테스트 ≠ QA.** 테스트는 제품을 보는 사후 활동, QA는 과정을 보는 예방 활동이다. 결함이 발견되면 테스트를 추가하는 것으로 끝내지 말고, **어떤 과정의 빈틈이 그 결함을 통과시켰는지**도 적는다.
- 테스트 목적은 맥락에 따라 다르다: 결함 발견, 커버리지 확보, 위험 감소, 요구사항 충족 검증, 규정 준수, 의사결정 정보 제공, 신뢰 구축, 완전성 확인. 작업마다 **이번 목적이 무엇인지** 먼저 정한다.

### 0.2 일곱 원칙

| # | 원칙 | 실무 규칙 |
|---|---|---|
| 1 | 테스트는 결함이 **있음**을 보이지 **없음**을 증명 못 한다 | "전부 통과"를 "결함 없음"으로 보고하지 않는다. **안 본 것**을 함께 쓴다. |
| 2 | 전수 테스트는 불가능하다 | 기법(§4)과 위험 기반 우선순위(§6)로 케이스를 고른다. |
| 3 | 이른 테스트가 싸다 | 요구사항 단계에서 인수 기준을 테스트 문장으로 쓴다. 코드 뒤에 붙인 테스트는 설계 결함을 못 잡는다. |
| 4 | 결함은 뭉쳐 있다 | 결함 이력이 있는 모듈에 테스트를 더 준다. 결함 이력이 위험 지도다. |
| 5 | 테스트는 닳는다 | 같은 회귀 스위트만 돌리면 새 결함을 못 잡는다. 결함마다 새 테스트를 추가하고 탐색 세션을 주기적으로 한다. |
| 6 | 테스트는 맥락에 따라 다르다 | 일회성 스크립트와 운영 시스템의 요구 수준은 다르다. 계획(§6.1)에서 수준을 명시한다. |
| 7 | "결함 없음"의 오류 | 결함이 없어도 사용자 목적에 안 맞을 수 있다. 검증과 확인은 별개다. |

### 0.3 용어 (보고서에서 이 뜻으로 쓴다)

- **오류(error)**: 사람이 저지른 실수. **결함(defect)**: 그 결과로 코드·문서에 남은 잘못. **실패(failure)**: 결함이 실행되어 드러난 잘못된 동작. **근본 원인(root cause)**: 그 오류를 낳은 상황.
- **테스트 기반(test basis)**: 테스트를 뽑아내는 근거 = 요구사항·인수 기준·사용자 지시·결함 이력.
- **테스트 조건**: "무엇을 시험할지"의 한 항목. **테스트 케이스**: 전제조건·입력·기대 결과가 있는 실행 단위. **커버리지 항목**: 기법이 정의하는 "빠짐없이 밟아야 할 칸".
- **추적성(traceability)**: 요구사항 ↔ 테스트 조건 ↔ 케이스 ↔ 결과 ↔ 결함이 연결되는 것. 테스트 이름에 요구사항 번호나 결함 식별자를 넣는 이유다.

## 1. 테스트 프로세스 — 작업마다 이 순서를 밟는다

작은 작업은 각 단계가 한 줄이어도 되지만 **건너뛰지는 않는다.**

| 활동 | 하는 일 | 산출물 |
|---|---|---|
| 1. 계획 | 목표·범위·위험·실행할 계층·완료 기준을 정한다 | 테스트 계획 (§6.1 템플릿, 요구사항 문서 안의 한 절) |
| 2. 모니터링·통제 | 진행을 계획과 비교하고 어긋나면 조정한다 (예: 환경 불가 → 대체 수단 명시) | 중간 보고 |
| 3. 분석 | 테스트 기반에서 **테스트 조건 목록**을 뽑고 위험순으로 정렬한다. 기반 문서의 모순·빈칸을 여기서 발견한다 | 테스트 조건 목록 (착수 전 합의) |
| 4. 설계 | 조건을 케이스로 구체화한다. 기법(§4)으로 커버리지 항목을 정하고 데이터·환경 요구를 정한다 | 케이스 목록·데이터/환경 요구 |
| 5. 구현 | 테스트 코드·픽스처·스크립트·실행 순서를 만든다. 환경을 세우고 정상임을 확인한다 | 테스트 스위트 |
| 6. 실행 | 계층별로 돌리고 결과를 기록한다. 이상은 원인까지 분석한다 | 실행 로그·결함 보고 |
| 7. 완료 | 미해결 결함을 기록하고, 재사용할 테스트웨어를 보존하고, 교훈을 남기고, 완료 보고를 쓴다 | 완료 보고 (§6.6 템플릿) |

**분석 단계 규칙**: 조건 목록에 요구사항에 안 보이는 아키텍처 조건을 반드시 넣는다 — 멱등성(같은 입력 두 번), 동시성, 재시작·복구(상태 파일이 없거나 반쯤 써졌을 때), 부분 실패(요청은 갔는데 응답을 못 받음), 시간(시간대·경계 초·윤년), 외부 응답의 0·빈값·오류 코드·형식 변화.

## 2. 테스트 레벨과 타입

### 2.1 다섯 레벨

| 레벨 | 대상 | 잡는 것 | 언제 |
|---|---|---|---|
| 컴포넌트(단위) | 함수·모듈 단독. 외부 의존 없음 | 계산·파싱·분기·경계 | 코드 변경마다 |
| 컴포넌트 통합 | 모듈끼리 실제로 엮음. 대역은 외부 경계에만 | 배선 누락·인터페이스 불일치 | 모듈 경계를 건드렸을 때 |
| 시스템 | 전체 경로를 끝까지. 부작용(전송·결제·삭제)만 차단 | 입력→결과 전 구간의 누락·오판 | 배포 전, 결함 수정 후 |
| 시스템 통합 | 실제 외부 시스템에 읽기 전용 또는 샌드박스로 접속 | 외부 응답 형식 변화·제한·지연 | 외부 스펙 변경 가능성이 있을 때 |
| 인수 | 사용자 관점의 확인. 드라이런 → 제한 운영 → 사용자 승인 | "원한 것이 이것인가" | 출시·전환 시 |

- 레벨마다 **목적이 다르다**. 단위가 많다고 통합을 생략하지 않는다(배선 누락은 단위로 못 잡는다).
- 각 레벨의 **진입 기준**은 아래 레벨 초록불, **완료 기준**은 그 레벨의 커버리지 항목 전부 실행과 미해결 결함 기록이다.

### 2.2 타입

- **기능 테스트**: 무엇을 하는가 — 완전성·정확성·적절성.
- **비기능 테스트**: 얼마나 잘 하는가 — 성능 효율, 호환성, 사용성, 신뢰성(복구·재시작), 보안(비밀값 유출), 유지보수성, 이식성, 안전성(ISO/IEC 25010). 비기능도 가능한 한 낮은 레벨에서 일찍 시작한다.
- **블랙박스**: 명세에서 뽑는다. 구현이 바뀌어도 살아남는다. **화이트박스**: 구조에서 뽑는다. 명세가 빈약할 때 강하지만 "빠진 요구사항"은 못 잡는다. 둘 다 쓴다.
- **확인 테스트**: 수정이 그 결함을 없앴나. **회귀 테스트**: 수정이 다른 곳을 깨뜨리지 않았나. 회귀는 영향 분석으로 범위를 정하고 자동화 1순위다.

### 2.3 유지보수 테스트 — 운영 중 변경의 트리거

1. **수정**(핫픽스·개선): 영향 분석 먼저. 무엇이 연결돼 있고 어떤 복사본(설정·문서·감시)이 같이 바뀌어야 하나. 배포 전 배포 대상의 현재 상태와 로컬을 대조한다.
2. **환경 변경**(런타임 버전·플랫폼·외부 API 버전·데이터 이관): 새 환경에서 스위트 재실행. 데이터 이관은 변환 결과를 검증한다.
3. **폐기**: 아카이브 무결성, 복원 가능성, 남은 배선(스케줄러·감시·참조) 제거를 검증한다.

## 3. 정적 테스트 — 실행 없이 잡는 것

실행 전에 읽어서 잡는 결함이 가장 싸고, 실행으로는 못 잡는 결함(도달 불가 코드, 문서 결함, 설계 결함)도 있다.

1. **리뷰** — 요구사항·설계·코드·설정·배포 절차.
   - 착수 전 요구사항 리뷰: 모순·모호·빠짐·중복을 찾아 **질문으로** 되돌린다. 추측해서 채우지 않는다.
   - 배포 전 코드 리뷰: 변경 diff 전체를 다시 읽는다. **자동 치환·정규식 패치는 결과물을 눈으로 확인**한다.
   - 형식은 목적에 맞춘다: 비공식 리뷰(이상 발견) < 워크스루(저자 주도, 이해 공유) < 기술 리뷰(합의·결정) < 인스펙션(가장 형식적, 저자는 리더·기록자 불가). 작은 단위로 나눠 리뷰한다.
   - 리뷰 체크리스트(§9)를 쓴다. 결함이 나올 때마다 갱신하고, 자동화 가능한 항목은 체크리스트에서 빼서 테스트로 옮긴다.
2. **정적 분석** — 린트·타입 검사·죽은 코드·미사용 변수·복잡도·취약점. CI에 넣는다.
3. **배포 대상 대조** — 배포할 곳의 현재 파일·설정·스케줄 항목을 로컬과 대조한다. 값이 아니라 지문(해시)으로 본다.

정적이 잘 잡는 것: 요구사항 모순, 인터페이스 불일치(파라미터 개수·타입·순서), 도달 불가·중복 코드, 표준 위반, 테스트 기반 커버리지 구멍(인수 기준에 대응 테스트 없음).
정적이 못 잡는 것: 데이터 의존 실패, 타이밍, 외부 응답 변화 → 동적 테스트가 필요하다.

## 4. 테스트 기법 — 케이스를 "체계적으로 적게" 뽑는 법

4.1~4.4는 코드에 해당 구조가 있으면 **의무 적용**이다.

### 4.1 동등 분할 (Equivalence Partitioning)

- 같은 방식으로 처리될 값들을 한 칸(partition)으로 묶고, **칸마다 최소 1개** 값을 시험한다. 유효 칸과 **무효 칸** 둘 다.
- 칸은 겹치지 않고 비어 있지 않아야 한다. 입력뿐 아니라 출력·설정·내부 상태·시간·외부 응답에도 적용한다.
- 무효 칸은 **케이스당 하나만** 넣는다. 둘 넣으면 한 결함이 다른 결함을 가린다(defect masking).
- 파라미터가 여럿이면 최소 기준은 **Each Choice** — 각 파라미터의 각 칸이 한 번 이상 등장. 조합의 의미가 있으면 결정표(4.3)로.

### 4.2 경계값 분석 (Boundary Value Analysis) — **모든 임계값에 3값 BVA 의무**

- 순서 있는 칸의 **양 끝**이 경계다. 결함은 경계가 한 칸 어긋나거나 빠진 데서 난다.
- **2값 BVA**: 경계값 + 인접 칸의 이웃. **3값 BVA**: 경계값 + 양쪽 이웃. `x ≤ 10`을 `x == 10`으로 잘못 짠 결함은 3값(9, 10, 11)이어야 잡힌다.
- 경계는 숫자만이 아니다: 빈 컬렉션/1개/많음, 문자열 길이 0/1/최대, 기간의 시작/끝, 시간 경계(자정·월말·시간대), 정밀도·단위 경계(정수/실수, 소수 자릿수), 잔량이 정확히 한도와 같을 때.
- 부동소수·단위 혼합 경계에서는 **반올림 방향**을 명시적으로 시험한다.

### 4.3 결정표 (Decision Table) — **조건 조합 로직에 의무**

- 조건 조합이 행동을 결정하는 로직은 **전체 조합 표**를 먼저 쓴다. 조건은 행, 규칙은 열. `T / F / –(무관) / N/A(불가능)`, 행동은 `X`.
- 커버리지 항목 = **실현 가능한 열 전부**. 불가능 조합은 삭제, 무관 조건은 병합해 줄인다. 조건이 많으면 위험 기반으로 열을 고른다.
- 표를 쓰는 과정 자체가 요구사항의 **빈칸·모순**을 드러낸다. 빈칸은 코딩 전에 질문한다.

예시 형식:

| 조건 | R1 | R2 | R3 | R4 |
|---|---|---|---|---|
| 조건 A | T | F | F | F |
| 조건 B | – | T | F | F |
| 조건 C | – | – | F | T |
| **행동** | 무시 | 대기 | 거부 | 실행 |

### 4.4 상태 전이 (State Transition) — **수명주기가 있는 객체에 의무**

- 상태·이벤트·전이·가드·행동을 그린다(`이벤트 [가드] / 행동`). **상태표**로 바꾸면 **무효 전이(빈 칸)** 가 드러난다.
- 커버리지 3단계: 모든 상태 < **모든 유효 전이(0-switch, 기본 요구)** < 모든 전이(무효 전이 시도 포함, 중요 경로엔 이걸 요구).
- 무효 전이는 케이스당 하나만 시도한다.
- "요청은 갔는데 결과를 모름(unknown)" 같은 중간 상태에서의 전이를 빼먹는 것이 결함 단골이다. 반드시 넣는다.

### 4.5 화이트박스 — 구문·분기 커버리지

- **구문 커버리지**: 모든 실행문이 한 번은 실행됨. **분기 커버리지**: 모든 조건 분기(if/switch/루프 탈출)의 양쪽이 실행됨. 분기 100%는 구문 100%를 포함한다(역은 아님).
- 중요 경로(부작용이 있는 경로: 쓰기·전송·삭제·결제)는 **분기 100%** 를 목표로 한다. 일회성 스크립트에는 요구하지 않는다.
- 분기를 다 밟아도 경로·데이터 의존 결함은 남고, "빠진 요구사항"은 못 잡는다. 블랙박스와 함께 쓴다.
- 화이트박스는 실행 전 **코드 드라이런(머릿속 실행)** 에도 쓴다. 패치 후 "이 입력이 들어오면 어느 줄을 지나 어디서 부작용이 나나"를 손으로 따라간다.

### 4.6 경험 기반 — 오류 추측·탐색·체크리스트

**오류 추측 / 결함 공격(fault attack)**: 과거 결함·개발자가 자주 하는 실수·비슷한 시스템의 실패 유형으로 목록을 만들고 공격한다. 범용 시작 목록(프로젝트 부록에서 확장한다):

- 입력: 올바른 입력 거부, 파라미터 누락·순서 오류, 인코딩·공백·대소문자.
- 출력: 형식 오류, 단위 혼합, 반올림 방향, 빈 결과를 성공으로 표시.
- 로직: 빠진 케이스, 연산자 반전(`<` vs `<=`), 경계 한 칸 오차, off-by-one.
- 계산: 정수 오버플로, 0으로 나눔, 정밀도 손실, 부동소수 비교.
- 인터페이스: 호출이 배선에서 빠짐, 파라미터 타입·개수 불일치, 버전 불일치.
- 데이터: 초기화 누락, 상태 파일 손상·부재, 비원자적 쓰기, 중복 키.
- 동시성: 같은 자원 동시 접근, 순서 의존, 재진입.
- 복구: 재시작 후 중복 실행, 부분 실패 후 상태 불일치.
- 외부: 제한(429)·거부(403)·빈 본문·필드 변경·지연·시계 불일치.
- 비밀값: 키·토큰이 로그·알림·아카이브·대화에 찍힘.
- 복사본 불일치: 같은 값을 복사해 둔 설정·문서·감시 중 하나만 바뀜.
- 감시: 대상이 없어졌는데 경보만 남음, 대상이 바뀌었는데 개수만 셈.

**탐색 테스트**: 명세가 빈약하거나 새 외부 시스템을 처음 붙일 때. **시간을 정하고(예: 30분) 차터(목표)를 적고** 시작한다. 설계·실행·평가를 동시에 하며 세션 시트에 발견을 적고, 끝나면 정식 테스트로 옮길 것을 고른다. 세션 중에도 경계값·동등분할을 즉석에서 쓴다.

**체크리스트 테스트**: 리뷰·배포·폐기에 쓴다. 항목은 질문형이고 개별로 확인 가능해야 한다. 자동화 가능한 항목, 진입·완료 기준에 더 맞는 항목, 너무 일반적인 항목은 넣지 않는다. 결함 분석 때마다 갱신하되 길어지지 않게 유지한다(§9).

### 4.7 협업 기반 — 사용자 스토리·인수 기준·ATDD

- 요청을 사용자 스토리로 읽는다: "[역할]로서 [목표]를 원한다, [가치] 때문에". 스토리는 카드·대화·확인(인수 기준)의 3C로 완성된다.
- INVEST(독립·협상가능·가치·추정가능·작음·**테스트가능**). "어떻게 테스트할지 모르겠다"면 스토리가 불명확하거나 가치가 없다는 신호 → 질문한다.
- **인수 기준**은 두 형식 중 하나로 쓴다: 시나리오형(Given/When/Then) 또는 규칙형(입력→출력 표, 검증 목록). 범위 정의·합의·긍정과 부정 시나리오·추정의 근거가 된다.
- **ATDD**: 인수 기준을 먼저 테스트 문장으로 쓰고, 그 다음 코드를 만든다. 긍정 → 부정 → 비기능 순. 테스트는 스토리의 모든 특성을 덮되 넘어가지 않고, 두 테스트가 같은 특성을 중복 검증하지 않는다. 자동화 프레임워크 형식으로 쓰면 실행 가능한 요구사항이 된다.
- **테스트 우선(Red→Green→Refactor)은 조건부**다: 목표가 명확하고 검증 가능하면 적용, 탐색·비결정적 의존·레거시면 생략하고 **"생략 + 이유 + 대신 무엇으로 확인"** 을 보고한다.

## 5. 자동화·도구

- 회귀·반복 비교·커버리지 측정·정적 분석은 자동화한다. 사람 판단(요구 타당성·사용자 의도 확인·탐색)은 자동화하지 않는다.
- 자동화의 이익: 반복 노동 제거, 일관성, 객관적 측정, 빠른 피드백. 위험: 도구 과신(초록불 = 안전 착각), 유지비 과소평가, 대역이 실제와 멀어짐, 플랫폼 호환(로컬과 배포 환경의 런타임 버전 차이), 도구 종속.
- **변이 검증**을 습관화한다: 테스트가 정말 잡는지 확인하려고 코드에 고의 결함(경계 한 칸, 조건 반전, 호출 삭제)을 넣고 붉은불이 켜지는지 본다. 붉어지지 않는 테스트는 테스트가 아니다. 보고에 "변이 n/n"으로 쓴다.
- 픽스처는 **실제 데이터 저장본**을 우선한다. 손으로 지은 대역은 외부 경계에서만. 픽스처 파일 안에 출처(언제·어디서·어느 버전)를 적는다.
- 테스트 이름에 **요구사항 번호·결함 식별자·날짜**를 넣어 추적성을 만든다.
- 반복 데이터는 for 루프가 아니라 파라미터라이즈드 테스트로 쓴다. 루프는 어느 케이스가 깨졌는지 못 알려주고 뒤 케이스를 실행하지 않는다.
- 배포 환경의 런타임 버전으로도 한 번 돌린다.

## 6. 관리 — 계획·기준·우선순위·위험·보고·형상·결함

### 6.1 테스트 계획 (요구사항 문서 안의 한 절, 5~15줄)

```
테스트 계획
- 범위/목표: 무엇을 어느 수준까지 (중요 경로 분기 100% / 스크립트는 산출물 검증만)
- 테스트 기반: 요구사항 §n, 사용자 지시 "…", 결함 이력 […]
- 가정·제약: 환경·데이터·시간
- 위험 상위 3 (가능성×영향) → 각각 대응 테스트
- 레벨/타입: 단위·통합·시스템·외부·인수 중 무엇을 언제
- 기법: 3값 BVA 대상 경계 목록, 결정표 대상 로직, 상태전이 대상 객체
- 진입/완료 기준 (DoR / DoD)
- 환경/데이터: 픽스처, 샌드박스, 런타임 버전
- 생략 항목과 이유
```

### 6.2 진입·완료 기준

- **진입(Definition of Ready)**: 인수 기준이 테스트 가능한 문장으로 있음, 경계 조건 질문이 답변됨, 데이터·환경이 있음, 이전 레벨 초록.
- **완료(Definition of Done)**: 계획한 커버리지 항목 전부 실행, 실패 0 또는 실패 전부 결함으로 기록, 회귀 스위트 자동화, 미해결 위험 보고.
- 시간·예산 소진도 완료 사유가 될 수 있으나, 그때는 **남은 위험을 사용자에게 보고하고 승인**을 받는다. 스스로 범위를 줄이지 않는다.

### 6.3 우선순위·견적

- 실행 순서 = **위험 기반**(영향 큰 경로 먼저) → 커버리지 기반(추가 커버리지가 큰 것 먼저) → 요구사항 우선순위. 의존 관계가 있으면 선행 테스트 먼저. 자원(환경·시간창) 가용성을 반영한다.
- 견적은 비율(과거 개발:테스트 비), 외삽(최근 반복의 평균), 전문가 합의(Wideband Delphi/플래닝 포커), **3점 추정** `E=(a+4m+b)/6`, 오차 `(b−a)/6`. "얼마 걸리나"에 한 숫자로 답하지 않는다.

### 6.4 테스트 피라미드·사분면

```
        [인수 / 사용자 확인]        ← 적게, 느림, 고립도 낮음
       [시스템 통합 (실제 외부)]
      [시스템 (전체 경로, 부작용 차단)]
     [컴포넌트 통합 (모듈 배선)]
  [컴포넌트/단위 (순수 함수·경계·결정표)]   ← 많이, 빠름, 고립도 높음
```

- 위로 갈수록 느리고 넓고 고립도가 낮다. 아래층이 두꺼워야 하고, 위층은 적어도 있어야 한다.
- 사분면: Q1 기술·팀 지원(단위·통합, 자동, CI) · Q2 비즈니스·팀 지원(인수 기준 예시·API·시뮬레이션) · Q3 비즈니스·제품 비평(탐색·사용성·사용자 인수) · Q4 기술·제품 비평(스모크·비기능). 네 칸이 다 있는지 계획에서 확인한다.

### 6.5 위험 관리

- 위험 = **가능성 × 영향**. **제품 위험**(잘못된 기능, 계산 오류, 런타임 오류, 성능, 보안, 데이터 손실)과 **프로젝트 위험**(외부 의존 변경, 자원·시간, 기술 부채)을 나눠 적는다.
- 위험 분석(식별 → 평가·등급) 결과가 테스트 범위·레벨·기법·커버리지·순서·노력 배분을 정한다. 결함 이력이 있는 영역은 가능성을 높게 잡는다.
- 대응: 테스트로 완화 / 수용(사용자 승인) / 이전(드라이런·샌드박스·제한 운영) / 비상계획(감시·자동 정지·롤백). 무엇을 골랐는지 계획에 쓴다.
- 위험 모니터링: 완화가 실제로 효과가 있는지, 새 위험이 생겼는지를 운영 감시·정기 회귀·정기 점검으로 본다.

### 6.6 모니터링·보고 — 완료 보고 형식 (의무)

```
테스트 결과
| 계층 | 실행 | 통과/실패 | 비고 |
| 단위 | ✅ | n/n (신규 k) | 변이 m/m |
| 통합 | ✅ | n/n | |
| 시스템 | ✅ | n/n | 픽스처 출처 |
| 외부 | ⏭ 생략 | – | 이유 |
| 배포 환경 | ✅ | n/n | 런타임 버전 |
- 커버리지: 경계 3값 BVA n/n, 결정표 n/n 열, 상태전이 n/n 전이, 분기 n%
- 확인 테스트: [실패 재현 테스트] 통과 / 회귀: 전체 통과
- 미해결 결함·남은 위험: …
- 이번 작업에서 보지 않은 것: …
```

- 지표는 진행(실행/미실행), 결과(통과/실패), 결함(발견/수정·밀도), 커버리지, 위험(잔여), 비용으로 나눠 쓴다. "통과"만 쓴 보고는 미완이다.
- 실패는 실패라고, 출력과 함께 쓴다. 건너뛴 것은 건너뛰었다고 쓴다. 독자에 맞춰 상세도를 조절하되 사실은 바꾸지 않는다.
- 진행 보고(작업 중)와 완료 보고(끝)를 구분한다. 완료 보고에는 계획 대비 편차·장애와 우회·교훈을 포함한다.

### 6.7 형상 관리

- 테스트 코드·픽스처·기대값·환경 정의는 제품 코드와 같은 버전으로 관리한다. 픽스처의 출처·버전을 파일 안에 적는다.
- 배포 단위(코드+설정+스케줄+감시)를 하나의 기준선(baseline)으로 본다. 기준선 변경은 승인 경위와 함께 기록한다. 이전 기준선으로 되돌려 결과를 재현할 수 있어야 한다.
- 배포 대상과 로컬의 **지문 대조**가 형상 관리의 최소 실행이다.

### 6.8 결함 보고 형식

```
- 식별자·제목: 한 줄 요약 (증상 + 위치)
- 발견 일시·발견 경로(어느 테스트/감시/사용자 보고)·보고자 역할
- 대상: 모듈/버전(해시)/환경(런타임·플랫폼)
- 맥락: 실행 중이던 테스트·활동·기법·데이터
- 재현: 최소 단계·입력·픽스처·로그 발췌
- 기대 결과 vs 실제 결과
- 심각도(영향) / 우선순위(고칠 순서)
- 원인(결함) / 근본 원인(과정) / 수정 / 확인 테스트 이름
- 상태: 열림·보류·중복·수정됨·확인 대기·재오픈·닫힘·기각
- 참조: 요구사항·테스트 케이스
```

- 이상(anomaly)이 전부 결함은 아니다. 오탐·변경 요청으로 판명되면 그렇게 적고 닫는다. 정적 분석의 지적도 같은 흐름으로 다룬다.

## 7. 테스트 작성 규칙 (금지·권장)

- private 메서드·내부 클래스를 직접 테스트하지 않는다. 공개 API로만.
- Mock을 최소화한다. 대역은 외부 경계(네트워크·시계·파일시스템·비밀값)에만. 내부 모듈은 실제로 엮는다. 대역이 늘수록 "테스트는 통과하는데 운영에서 깨지는" 가정이 커지고 리팩터링을 막는다.
- 상태 검증(무엇을 반환·기록하는가)을 행위 검증(어떤 순서로 무엇을 불렀나)보다 우선한다.
- 반복 데이터는 파라미터라이즈드. 무효 입력은 케이스당 하나.
- public API가 다 테스트되는데도 불안한 private 코드는 필요 없는 코드일 수 있다. 지워보고 돌린다.
- 비결정적 요소(시간·난수·네트워크)는 주입해 결정적으로 만든다. 그래도 안 되면 상위 계층으로 올리고 단위에서는 뺀다.
- 테스트는 실패 이유를 메시지로 말해야 한다: `assert.equal(a, b, "두 요청이 서로 다른 식별자를 써야 함")`.
- 테스트 하나는 한 가지를 검증한다. 여러 단언이 있어도 하나의 조건에 대한 것이어야 한다.

## 8. 중요 경로 추가 관문 (부작용이 큰 경로: 결제·전송·삭제·외부 쓰기)

프로젝트 부록에서 구체화한다. 범용 최소선:

1. 해당 경로 **분기 100%** + 결정표 전 열 + 상태전이 전 전이(무효 포함).
2. **변이 검증** 통과: 최소 3종(경계 한 칸, 조건 반전, 부작용 호출 삭제)에서 붉은불.
3. **드라이런**: 실제 입력으로 부작용 직전까지 도달하고 계획이 로그에 남는다. "돌긴 도는데 아무것도 안 하는" 실패 모드를 생존 신호만으로 판단하지 않는다.
4. 운영 **감시·회귀 자동 실행·정기 감사**가 배선됨 — 감시는 개수가 아니라 대상으로.
5. 배포 전 **대상 지문 대조**, 배포 후 **확인 테스트**(배포 환경에서 스위트 재실행 + 첫 실제 입력 처리 로그 확인).
6. 승인이 필요한 설정값은 변경 없음 또는 승인 경위 기록.
7. 비밀값이 로그·알림·아카이브·대화에 없음.
8. 첫 운영은 제한된 범위(소량·일부 사용자)로, 결과를 보고한 뒤 확대.

## 9. 체크리스트

**착수 전**
- [ ] 목표 한 줄과 인수 기준(GWT 또는 표)이 있다
- [ ] 경계 조건 질문(0개/1개/비정상/중복/동시/재시작)이 답변됐다
- [ ] 테스트 조건 목록을 만들고 위험순으로 정렬했다
- [ ] 변경 가능성 목록의 항목이 대역 경계와 일치한다
- [ ] 결함 이력을 읽고 결함 공격 목록에 반영했다
- [ ] 테스트 계획(§6.1)이 요구사항 문서에 있다

**완료 전**
- [ ] 모든 임계값에 3값 BVA, 모든 조건 조합에 결정표, 모든 수명주기에 상태전이
- [ ] 확인 테스트 + 회귀 스위트 전체 초록
- [ ] 변이 검증 n/n
- [ ] 배포 환경 런타임에서도 초록
- [ ] 대상 지문 대조 → 배포 → 배포 후 확인
- [ ] 완료 보고서(§6.6) — 계층·통과/실패·생략·미해결·안 본 것
- [ ] 새 결함·기각은 결함 보고 형식(§6.8)으로 기록
- [ ] 결함 공격 목록·체크리스트에 추가할 것이 있는지 확인

# cpk 테스트와 온라인 검증의 한계

## 스위트

| 스위트 | 네트워크 | HOME | 판정 기준 |
|---|---|---|---|
| `test_unit` | 없음 | 임시 | 파서·쿠키·상태·관문 로직 |
| `test_regression` | 없음(가짜 CDP/HTTP) | 임시·실제 flock | 과거 결함 재발 방지 |
| `test_functional` | 실제 쿠팡 | **운영 state** | 브라우저 검색 결과 |
| `test_integration` | 실제 쿠팡 | **전용 임시** | 브라우저 재발급→헬스→수집 전 구간 |
| `audit_81a7aa1.py` | 없음(실제 flock·프로세스) | 임시 | 요청 제어 16 시나리오(정규 test_* 아님) |

```sh
sh tests/run_all.sh offline   # unit + regression (어디서나)
sh tests/run_all.sh online    # functional (맥미니, 차단 구간 자동 skip)
sh tests/run_all.sh full      # integration (맥미니 + Chrome)
```

## 온라인·통합의 공통 제어 공유 한계 (중요)

CPK의 중단·예산·간격은 `CPK_HOME/control.json`과 그 옆 파일 잠금으로 **HOME 단위**로 공유된다.
그런데 두 온라인 스위트의 HOME 범위가 다르다.

- **`test_functional`은 운영 `state` HOME으로 실행**하면 운영 `control.json`을 그대로 공유한다.
  즉 운영이 중단(pause) 중이면 이 테스트도 새 요청을 보내지 않고, 테스트가 보낸 요청도 운영
  예산·간격에 함께 집계된다. 이건 의도된 동작이지만, 실제 쿠팡 요청을 소비하므로 저빈도로만 돌려야 한다.
  다른 HOME으로 돌리면 운영 중단·예산과 분리되어 같은 IP인데도 제어가 끊긴다.

- **`test_integration`은 전용 임시 HOME·전용 포트(9333)·전용 프로필로 실행**한다. 운영 Chrome(9222)을
  건드리지 않으려는 격리다. 그 대가로 **운영 `control.json`·요청 잠금과 분리**된다. 따라서 통합 테스트가
  실제 쿠팡에 접속하는 동안에는 **운영의 중단·예산을 존중하지 않는다.** 같은 외부 IP를 쓰므로,
  운영이 차단으로 중단된 상태에서 통합 테스트를 돌리면 그 IP로 새 요청이 나가 상황을 악화시킬 수 있다.

### 결론과 운영 규칙

- 통합 테스트(`full`)는 **운영이 중단 상태가 아닐 때만** 수동으로 돌린다. 자동·주기 실행하지 않는다.
- 온라인 실검증이 운영 제어를 반드시 존중해야 한다면, 전용 HOME이라도 **control.json과 요청 잠금만은
  운영 경로를 공유**하도록 구현해야 한다(데이터·쿠키 HOME은 분리하되 제어 상태만 공유). 현재는 미구현이며,
  그때까지 통합 테스트의 온라인 실행은 위 수동 규칙으로 제한한다.

## 판정 기준을 운영 경로에 맞춘 이유

과거 `test_functional`은 파이썬 경로(`cs.canary`/`cs.refresh`/구형 `search_html`)로 "세션이 살아 있나"를
판정했다. 파이썬 요청은 지문 때문에 상시 403이라, **실제 브라우저 검색이 60건 잘 되는 순간에도**
"아카마이 차단 구간"으로 전부 skip됐다(구형 `sr.search`는 CLI 폐기 때 제거되어 세션이 열려도 에러).
현재는 브라우저 경로(`cb.search`)로 판정·검증한다 — 운영과 같은 경로여야 결과가 신뢰된다.
